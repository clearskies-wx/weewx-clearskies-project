## Layer Responsibilities

Computation boundaries between the three application layers. **No chart-specific or visualization-specific endpoint in the API.** The API is a general-purpose data access layer (ADR-010); chart-type awareness belongs in the dashboard.

| Layer | Responsibility | Does NOT do |
|-------|---------------|-------------|
| **API** | General-purpose data access AND transformation: query the weewx archive, serve raw observation/aggregate values, host provider modules, expose setup endpoints. Unit conversion, derived-value computation (Beaufort scale, comfort index, barometer trend direction, cardinal wind directions). Enrichment pipeline (conditions text, weather text, barometer trend, wind rolling window averages, scene descriptor). SSE streaming at `GET /sse`. Single conversion authority (ADR-042, ADR-058). | Chart-specific binning or aggregation, presentation formatting, chart-type awareness, UI control plane (page visibility, card layout — these are static config served by Caddy, not API concerns). |
| **Dashboard** | Rendering + presentation-level computation: display converted values, client-side binning for visualizations (e.g., wind rose direction×Beaufort matrix from API-provided fields), LTTB downsampling, chart layout, theming, accessibility. Page visibility filtering from `pages.json`. Dynamic Now page card rendering from `now-layout.json` and the card plugin registry (ADR-064). | Unit conversion, Beaufort/comfort-index threshold logic, raw SQL queries, provider API calls. (ADR-042: "Dashboard does not carry Beaufort thresholds.") |

**Why the computation boundary matters (ADR-041 amendment 2026-06-05, updated for ADR-058):** The API is the single conversion and enrichment authority. Chart-type-specific logic (binning, aggregation for a specific visualization) belongs in the dashboard. A proposed API endpoint that requires domain-specific computation — Beaufort classification, comfort index, conditions text — belongs in the API's enrichment pipeline, not as a raw data endpoint. The dashboard reads API-provided derived fields (like `beaufort.value`) but does not recompute them from raw observations.

> **⚓ MARINE HANDOFF MODEL — read this before touching SWAN or the surf pipeline.** (Scannable summary of the detailed paragraphs below; if this ever disagrees with them or with `services/invariants.py`, those win — fix this.)
> - **SWAN never models the break zone.** It computes the wave field on nested grids (L1 1 km → L2 → L3 → L4) and hands the spectrum to a separate **1-D surf model** (`services/surf_1d_analytical.py`, "SwellTrack") that runs **from the handoff to shore and does the breaking.** Its *landward* boundary is **HAT (up the beach face), not the still-water shoreline** — sized once at setup so the moving shoreline stays inside the domain at every tide (ADR-093 Amendment 4, TA-C18; see the SwellTrack landward-boundary paragraph below).
> - **The handoff is always *before* the break** — `break_depth ≤ handoff_depth`, *checked/observed* at runtime by **INVARIANT_1** (invariants log-and-observe; they do not raise or enforce — refusal lives in the Phase-C paths). For a fine-grid handoff (L4/L3) the depth tracks each forecast hour at `1.3 × Hs / 0.73` (≈30% seaward of that hour's breaking depth); the open-beach fallback hands off at the fixed **15 m** reference.
> - **Where it hands off — per transect, first-match-wins** (`services/transect_handoff.select_hourly_handoff()`): **(1)** transect enters the **structure grid (L4)** footprint → read from L4, close to shore, structure sheltering/diffraction baked in — *this is the HB-pier case*; **(2)** else a classified refraction feature with an **L3** → read from L3 (selection written but **not yet wired** — falls to rule 3 today); **(3)** else → **L2 at the fixed 15 m** reference (open beach / no obstacle, deeper water).
> - **Swell display card ≠ handoff.** The card's swell catalog comes from a **deep-water reference at the spot's own 15 m contour, always L2 (never L3/L4), and is NOT the 1-D model's starting point** (INVARIANT_7).
> - **DO NOT extend SWAN to shore / into the break zone.** The 1-D handoff exists precisely so SWAN does *not* model the surf zone (the 2026-07-25 grid-resize incident). Sampling the handoff inside the break zone (~2 m) was defect B — a bug, not the design.
> - **H-1 handoff-collapse instrumentation (2026-08-06).** The per-transect handoff selection's four silent `continue` exits (`swan_runner.py`'s `_select_l3_handoff_position_and_spectrum()`) are now cause-tagged and aggregated into one `H-1 handoff-collapse:` WARNING per affected hour; the 1-D pipeline's per-transect bulk-fallback branch is counted and, on the SWAN-cycle precompute path only, flags `GET /health` (`bulk_fallback: ...`) when a threshold fraction of transects fall back in one hour — see PROVIDER-MANUAL.md "Bulk-fallback health flag (H-1)".

> **⚙ GEOMETRY MODEL — how the study area's geometry is DERIVED (target, Marine Geometry-Model Plan; ADR-093 Amendment 5 + ADR-100).** These change *what bearing/exposure/open-water direction/axis is passed into* the existing sizing and handoff code — **not** the sizing formulas, the handoff surface, the convergence gate, the HAT landward boundary, the deep-water reference, or any SWAN command syntax (all OFF-LIMITS). Items whose code has not yet migrated are marked "(target — Phase GX)"; the detailed paragraphs below still describe the pre-geometry derivation until each phase lands.
> - **Shore-facing = the smoothed-0 m-shoreline normal (DSAS/CliffMetrics method), per-transect, operator-overridable** — the 0 m shoreline is traced from the finest bathymetry as an ordered polyline, its coordinates moving-average-smoothed over an alongshore window swept 500 → 2500 m until the heading stabilizes (≤ 5° change between windows), and beach facing / each transect bearing = the seaward perpendicular of the smoothed line's local tangent. **Not** the perpendicular of the operator-drawn segment (which delimits the surf area, never the facing), and **not** the superseded 2 m/5 m isobath ray-fit (produced ~202° vs true ~220° at HB; replaced by operator ruling 2026-07-31). Computed when the surf spot is being DEFINED: the wizard calls a new marine geometry endpoint (via the API) with just the drawn segment — the strip-bathymetry fetch and the computation depend on **nothing but the segment** (no SWAN grid or domain exists yet; L1–L4 are sized AFTER, *from* this facing, and a no-obstacle spot never has an L4 at all). The computed value pre-fills the wizard field; the operator may adjust; the confirmed value is stored in config with a source tag (`operator | computed | fallback_segment_perp` — only `operator` is an override). The config-push chain then derives only the per-transect bearings (retrying a `fallback`-tagged facing) and persists them to the spot profile — never during model runs. Degenerate shoreline falls back to the segment-perpendicular + WARNING. L2/L3 sizing is **coverage-driven** — it encloses the union of every transect's own offshore-contour reach, not one averaged bearing. (target — Phase G1R; AD-1R, superseding AD-1's method; the pinned equations live in MARINE-GEOMETRY-MODEL-PLAN §AD-1R.)
> - **L1 offshore aim + WW3 boundary sides = the open-water fetch fan, not `mean_offshore_bearing_deg`.** A new `services/geography.py` casts 72 rays (5°) from the study centroid to the regime horizon; a ray hitting land continues and tests for ≥5 km open water beyond (**directly-open / wrap-candidate / truly-blocked**). L1 aims along, and the WW3 boundary side is placed on, the open-water bearing. For a **wrap-candidate** (island/headland/peninsula with open water beyond) L1 is enlarged to **enclose the intervening land + the open water beyond** so SWAN computes the wrap-around. L1/L2 stay axis-aligned (aim/extent moves, never rotation). WW3 selection stays cardinal-only (N/E/S/W); its qualification criterion is unchanged. **Great Lakes:** L1 is sized from lake fetch (the fan's fetch value), not the ocean shelf. **IMPLEMENTED + DEPLOYED (Phase G2; AD-3, ADR-100; wired end to end marine `51543b1`, 2026-08-01)** — `services/swan_domain.py`'s `_compute_level1()` takes `open_water_bearing_deg`/`regime`/`fetch_value_km`/`rays`/`horizon_km`, and `services/grid_sizing_chain.py`'s apply-time chain passes all five from `geography_result` at both the L1-sizing call and the boundary-side call. The runtime path (`providers/nearshore/swan.py`) was the one piece still missing this wiring — it read `DomainSizing.open_water_bearing_deg` from the sizing cache but never passed it into `select_boundary_stations_with_cycle_fallback()`, so it silently fell back to beach facing; 51543b1 added the missing `offshore_bearing_deg=domains.open_water_bearing_deg` argument. `None` (a boxed-in spot, or a sizing cache written before this field existed) still falls back to the prior beach-facing behaviour.

> **SWAN nearshore model (ADR-093, corrected ADR-095, redesigned Phase 14).** The marine service's `[nearshore]` pip extra adds the SWAN Fortran binary (subprocess), wgrib2, the HRRR wind provider, and the GFS wind provider. SWAN executes a nested grid per cycle — **two levels always, up to four when a structure or a classified refraction feature is present** (Marine Model Restoration Plan Phase E, ADR-093 Amendment 3, superseding the prior three-level description below). Level 1 (1 km, coarse) covers the continental shelf approach from the GSFM shelf edge to shore; Level 2 (100 m, nearshore) covers shore to 30 m depth. Both always run. **Level 3 (`_L3_RESOLUTION_M` = 40 m, `services/swan_domain.py`) is need-driven and exists for exactly two reasons, never otherwise** (ADR-093 Amendment 3, plan task E4, operator ruling D2): (a) as the coarse nesting step under the structure grid (L4) — extent is L4's own footprint plus clearance of at least 2 L2 cells on every side, plus the cluster's alongshore pin span (`size_l3_coarse_nest()`), **not** the 30 m contour, which had no rationale once the collar fallback was struck; or (b) as the working refraction grid at an operator-classified point break, headland, or bay break — cross-shore span the 15 m contour to the per-hour breaking-depth contour, diffraction off. **Neither condition → no L3 at all**: `L1 → L2 → 1D at 15 m`, byte-identical to a spot with no structure and no classification — this is unchanged production behaviour, not a regression. **Level 4 (`StructureGridDomain`, `services/swan_domain.py`, fixed 10 m resolution per 2026-07-27 operator ruling — "just use a 10m grid for when L4 is needed, period") is the structure grid** — a TRUE rotated rectangle (SWAN `CGRID REG … alpc`/`NGRID … alpn`), not a lat/lon bbox. **Current design (marine `4e79d21`, 2026-08-01, R3 residual "L4-transect co-registration," reversing the OMBB-axis design below; ADR-093 Amendment 6):** `alpc`/`alpn` = the resolved **beach facing**, not a structure axis — the beach-frame bounding rectangle of every eligible structure's own footprint UNION the handoff points of every surf-area transect any one of them shadows (per-structure shadow test against the geography fetch fan's open rays, never a union footprint, so a gap between two structures is never itself shadowed). Shoreward edge = the minimum-`u` shadowed transect handoff point; seaward edge = the seaward-most footprint point + one wavelength margin (`compute_structure_grid_domain()`). Zero shadowed transects → L4 skipped. **No primary-structure selection** — every eligible structure in the cluster participates in one grid. An eligible structure (pier/jetty/groin/breakwater, `_STRUCTURE_GRID_ELIGIBLE_TYPES`) always also triggers L3's role (a) above, so **L4 always nests under L3, which nests under L2, which nests under L1: `L1 → L2 → L3 → L4`.** **Neither L3 nor L4 runs to shore** — SwellTrack and the SurfBeat strip model from the handoff (per the first-match-wins rule below) to the beach. Grid geometry is frozen at setup. The handoff itself is **not** a fixed depth: each forecast hour it sits at `1.3 × Hs(hour) / 0.73`, a 30% margin seaward of that hour's breaking depth, and the spectrum is read from whichever cell that lands in — a lookup, not a regrid; a computed handoff falling outside the grid clamps to the nearest interior station and logs a WARNING (T4A.9/T4A.10). **Since 2026-08-01 (BD-1/BD-2, `SURF-ZONE-BREAK-DETECTION-SPEC-2026-08-01`, marine `03b33e1`/`ea62e85`, ADR-093 Amendment 7) that lookup is further constrained: before selecting, the transect's full station band is scanned seaward→shore for the outermost suspected break zone (SWAN's own `Hs ≥ γ·depth` or QB over the existing threshold, both reused unchanged), and the selected station must land strictly seaward of it — never inside or shoreward of a break. This narrows which stations the SAME nearest-to-target-depth search may pick from; the target-depth formula and the clamp-to-nearest-interior behavior above are otherwise unchanged. When this constraint actually moves the pick, the published handoff depth follows the selected station's own depth rather than the untouched formula value (adversarial audit Finding F1) — see ADR-093 Amendment 7 and PROVIDER-MANUAL.md §14.15 for the full mechanism. No suspected break on a transect's band this hour → the unconstrained clamp-to-nearest-interior search described above, byte-identical to before.** **Which grid supplies that per-hour station is a first-match-wins choice, per transect (Marine Model Restoration Plan E5, ruling D3, 2026-07-27): (1) if the transect's cross-shore line enters the structure grid's (L4) footprint, read from L4, `source_level="L4"`; (2) else if the transect lies in a classified refraction feature covered by L3, read from L3, `source_level="L3"` (today's path, unchanged); (3) otherwise hand off from L2 at the fixed 15.0 m reference depth, `source_level="L2"` (unchanged production path). Neighbouring transects may resolve to different rules — that is accepted, not smoothed. Implemented in `services/transect_handoff.py`'s `select_hourly_handoff()`; the "touches L4" determination itself is data-presence at the caller (`swan_runner.py`), the same convention already used for L3 before this change. Rule 2 (L3 as a standalone classified-refraction grid for transects L4 does not cover) is written as pure selection logic but is NOT wired in the run path — L3 runs `grid_level="outer"` whenever it nests an L4 structure grid and emits no per-transect output of its own in that role, so an L4-uncovered transect at such a spot falls to L2 today, not L3; wiring rule 2 needs an outer/inner grid-role dispatch change and is a tracked, not-yet-closed gap.* **Phase 4B (approved 2026-07-25) makes the handoff per transect rather than per spot, and its core is IMPLEMENTED AND DEPLOYED** (T4B.1 `4492927`, T4B.3 `4dd8964`/`e9a1047`, T4B.4 in `swan_runner.py`; verified against git and the running services 2026-07-25). Each 1D line now reads the field at **its own** coordinates via a `POINTS` set, so the handoff varies in two dimensions: depth per hour, location per transect. Previously one `CURVE` was emitted per *spot* and its selected value replicated across every transect, discarding at the boundary the alongshore variation the 2D L3 grid computes — refraction around a structure, its shadow. **T4B.2 (SWAN watershed partitioning) is DONE, operator-approved 2026-07-25, deployed to librewxr (`12f9ddc`).** SWAN's own watershed partitions — read from `TABLE` `PTHSIGN`/`PTRTP`/`PTDIR`/`PTDSPR` columns — are now the production source of swell partitions at every live call site (the L2 deep-water-reference baseline and the L3 CURVE handoff), replacing the bespoke ±4-bin neighbourhood peak-finder (`decompose_spectrum()`). Real-data measurement across 67 spectra found that peak-finder reported one swell system two to five times rather than finding distinct systems (energy closure up to 227% of available energy, 65/65 multi-component timesteps over 105%); the earlier preliminary reading of that same evidence, recorded against this section, had it backwards. `decompose_spectrum()` remains in `services/swan_spectral.py`, unchanged, for `scripts/compare_partitioning.py`'s direct measurement of the two algorithms against each other — it has no production caller. A (point, timestep) with no PT* data available degrades to empty components plus a WARNING naming the spot and timestep; nothing is recomputed to fill the gap (no-silent-fallback rule). Still outstanding within Phase 4B: **T4B.6/T4B.7/T4B.8** (call-site wiring, ADR-093 Amendment 3, real-swell verification). Output at a point is interpolated from the computational grid (SWAN manual p. 90), so this is a sampling change, not a regrid. For L3-disabled spots the same applies to the L2 fallback, bounded by L2's 100 m resolution (~3 distinct cells across a 320 m spot — better than one, and the honest ceiling). **SurfBeat is deliberately excluded**: the IEM's biphase evolution equation assumes bottom slopes are "mild and alongshore uniform," so per-transect IG strips would assert precision the physics does not carry. **The grid's shoreward reach is ADR-093 Amendment 2 §2's breaking-depth criterion** — the smallest depth `1.3 × Hs / 0.73` ever produces for the spot, evaluated at a fixed design minimum swell (`_MIN_DESIGN_HS_M = 1.0` m, a module constant in `services/swan_domain.py` with the same status as gamma — not a config key). A setup-time viability test then decides: if the grid cannot reach the feature it exists for, L3 is disabled (logging which feature was unreachable and by how much) and the spot runs L1 → L2 → SwellTrack from ~15 m. Setup-time calculation is depth-based only — contour positions, slope, breaking depths, grid extents, relief; **no** contour-curvature or shoreline-shape analysis. **This paragraph describes L3's role (b) — the classified-refraction-feature grid, where the offshore edge does stay at the 15 m contour.** For role (a) — L3 nesting under a structure grid — the 15 m-contour offshore edge is **retired**: L3's extent there is driven by L4's footprint plus clearance, not the 30 m or 15 m contour (ADR-093 Amendment 3, operator ruling 2026-07-27, findings §0A D6 item 1: "Retire the 15 m-contour offshore edge; adopt the structure grid" — Approved). Spot clustering: adjacent surf spots <500 m apart share one Level 3 grid, reducing per-spot compute cost. Domain sizing is physics-based — Level 1 offshore extent is the GSFM shelf/slope boundary distance (Harris et al. 2014) plus a **10 km** margin (corrected 2026-08-02, H3/TC-24 item 3 — was documented as 15 km; verified against `services/swan_domain.py:1131-1132`, `offshore_km = shelf_dist_km + 10.0`, "per research brief §5"); Level 2 and 3 extents are depth-driven. Net effect: the next full run cold-starts on the new grid instead of warm-starting from a hotstart sized for the old one, and the E8 hourly fill's own `level1/INPUT`-reuse guard (`_reused_l1_boundary_command_lines()`) finds nothing and skips (its own WARNING) until the next full run rebuilds it. **A geometry-changing config push now also signals an immediate full run (F1 follow-on, operator ruling 2026-07-28: "it should immediately trigger a full run"), rather than waiting up to ~6h for the next extended HRRR cycle to rebuild what was just cleared.** `_cold_start_swan_if_geometry_changed()` sets a process-safe `threading.Event` (`grid_sizing_chain.force_full_run_signal`) whenever it clears the run state; `service.py`'s `_marine_runner_loop()` — the same process — peeks that signal at the top of every iteration (≤`check_interval_s`, 300s, so "immediate" means "at the next check," not synchronous with the config push) and, when set, forces a FULL (`run_all_spots()`) run that cycle, bypassing both the HRRR cycle-unchanged gate and the extended/intervening cadence branch (a geometry change needs a full rebuild, never the stationary fill). The signal is cleared only once that forced full run succeeds; a failure (e.g. a transient wind-fetch or SWAN error) leaves it set so the next iteration retries the forced full run rather than silently losing the trigger. SWAN *can* run as a subprocess within the API process on the same host, which is the bundled default for a single-host operator install. Hotstart files (`{level1,level2,level3_N}_hotstart.dat`) persist between runs so each cycle starts from the previous run's wave field (no cold-start spin-up). Per-level bathymetry cached at `/etc/weewx-clearskies/` as `swan_bathymetry_L1.json` (1 km spacing), `swan_bathymetry_L2.json` (100 m spacing), and `swan_bathymetry_L3_{hash}.json` (40 m spacing, one file per cluster bbox). **Bathymetry is requested for the domain PLUS one grid cell of that level's resolution, and a source is rejected unless it covers the whole domain (C-90, 2026-07-26).** Requesting exactly the domain box could never work: the resolvers subset with `sel(lat=slice(...), lon=slice(...))`, which returns only source cells *inside* the request, then `coarsen(..., boundary="trim")` discards the remainder — so the returned grid was always inset and the outermost ring of SWAN cells was filled with a fabricated 15 m depth (measured live before the fix: 652 fabricated cells across L1+L2; after: 0). **Source order is level-dependent** (operator ruling 2026-07-26). **L1's primary source is ETOPO 2022 15 arc-sec bed elevation (~460 m), pinned** — one global dataset (verified against the NCEI catalogue as spanning −180..180, −90..90) owns L1, so region-specific data acquisition is only ever an L2/L3 concern. L1 spans the shelf edge to shore, which most regional coastal DEMs cannot cover, and at 1 km resolution L1 gains nothing from 10 m data that is only coarsened away. **L2/L3 try the NCEI regional DEM first**, then ETOPO, then the unpinned mosaic. Great Lakes is tried ahead of the ocean sources wherever it applies. If no source covers the domain, the level **raises** rather than filling the gap. **The `getSamples` query is pinned to a single catalogue raster via `mosaicRule`/`lockRasterIds`**, because the `DEM_all` mosaic otherwise selects per point and can assemble one grid from DEMs on different vertical datums (NAVD 88, MHW and MSL all overlap in US coastal boxes). Pinning also recovers the datum: `getSamples` does not echo `VerticalDatum` per sample, which is the only reason this used to degrade to an invented unknown-datum placeholder label with a ~1 m bias warning (removed entirely at T8.11e — a source either publishes a datum or is unusable) — the datum was always published in the mosaic catalogue and is now read from it (`find_catalogue_raster()`, resolved by **name**; OBJECTIDs are service-rebuild artifacts and are never hardcoded). ETOPO reports "Sea Level", normalised to `LMSL`. A raster that cannot be found, or that publishes no datum, **raises** — a guessed datum is a metre-scale error applied uniformly across the grid. Data source priority chain (resolved by the marine service's `services/bathymetry_resolver.py`): (1) operator-supplied file (GeoTIFF/NetCDF/ASCII XYZ, operator specifies datum from the CO-OPS-supported list), (2) NCEI regional coastal DEM via OPeNDAP (~10m resolution, 199 DEMs indexed in `data/ncei_regional_dem_index.json`), (3) USGS Great Lakes seamless topobathymetric DEM (GeoTIFF, `rasterio` windowed read), (4) NCEI CRM/DEM_all fallback (~90m). Vertical datum consistency enforced by matching the CO-OPS tide prediction datum to the bathymetry DEM's native datum, and — since T8.11d — by requiring **every level to agree** before a run: `verify_level_datums_agree()` reads L1, L2 and each configured L3 cluster cache and refuses the run, naming each level and its datum, rather than stamping one level's datum on the others (ADR-098 criterion 9). The levels agreed in production only by coincidence — each looks its DEM up independently, and the same Huntington box offers MSL and NAVD 88 products side by side. **Ruled 2026-07-27 (C-103, ADR-098 as amended): the agreement guard is per region, because the common datum is per region, not global.** Great Lakes are non-tidal, so LMSL — a tidal datum — does not apply there; a Great Lakes domain's L1/L2/L3 must agree with each other on that lake's own `LWD_IGLD85` (NOAA's Low Water Datum on IGLD85), while ocean/tidal domains keep agreeing on LMSL as below. The two are never compared against each other. Great Lakes separations from LMSL/ocean scale are roughly 200× larger (~−176 m Lake Michigan, ~−173.5 m Lake Erie, vs. ~−0.83 m ocean) — implementation of the Great Lakes branch was in flight in the marine repo as of this writing; not yet marked complete. **Grid-wise unification of every level on LMSL, ocean/tidal domains only (T8.11b, `services/vertical_datum.py:convert_grid_to_lmsl()`).** Every L2/L3 grid is converted from its native published datum (NAVD 88, MHW, MHHW, MLLW, MLW) to LMSL **per cell**, at bathymetry-resolution time, before the grid is cached — no single domain-centre offset is applied anywhere. The conversion transforms NOAA's own compound CRS pair (e.g. `EPSG:6318+EPSG:5703` NAD83(2011)+NAVD88 → `NOAA:1761` NAD83(2011)+LMSL) through `pyproj`, reading NOAA's published VDatum `proj.db` and separation-grid TIFFs from a data directory installed separately at setup time (`VDATUM_GRIDS_DIR`, default `/var/lib/weewx-clearskies/vdatum-grids`, override `CLEARSKIES_VDATUM_GRIDS` — install procedure and size in OPERATIONS-MANUAL.md §1). ADR-098 (as amended 2026-07-26) named `vyperdatum` for this; that choice was reversed by operator ruling the same day in favour of reading the NOAA grid set directly through `pyproj`, which is already a marine dependency — see ADR-098 for the reasoning. L1 (ETOPO 2022) is already MSL and is treated as an LMSL alias, so it is passed through unconverted. Grid cells that fall on land have no defined LMSL separation (NOAA's surface is water-only); `convert_grid_to_lmsl()` fills those with the mean separation of the grid's own water cells rather than leaving them on the source datum, which would otherwise put a datum seam along the waterline (C-97). The conversion raises rather than returning a grid labelled LMSL if the NOAA authority did not load, if the resolved PROJ operation is ballpark, or if every cell's computed separation is exactly zero — the code's guard against the pyproj version silently falling back to a bundled database (see the pyproj pin note below). Do not "fix" an observed handoff/reference discrepancy at a structure or classified-feature spot by moving the reference off L2 — that is by design, so every spot's reference carries the same meaning regardless of its own grid configuration. Dissipation is Q_b-weighted and strictly one-sided (energy never flows from ocean to wave) and feeds a post-breaking roller-energy reservoir (Svendsen-family balance, decay coefficient 0.10) whose energy — not a fixed 0.707×Hs height ratio — now sizes whitewater/impact-zone extent; a fire-only closure invariant and a fire-only no-gain invariant (`services/invariants.py`) observe energy conservation in production. Wire field names/shapes are unchanged by this round. SWAN QB retained as diagnostic. **`(ruled 2026-08-10; lands with Phase K of MARINE-PAGE-FIXIT-PLAN)` — published break-marker/impact-zone target state (ADR-106 R3/R4, PA3/PA4) supersedes this paragraph's onset/cessation publication rule and its whitewater-extent criterion for the PUBLISHED path only; the Q_b solve, one-sided dissipation, and roller-energy reservoir described above are UNCHANGED.** Operator review found the cessation-gated marker rule glues a beach's outer and inner breaks into one zone whenever Q_b never drops below the cessation threshold between them, so a visibly-crashing beach break gets no marker. Target state: published marker detection DECOUPLES from cessation — every local dissipation maximum in a region where `Qb_i ≥ qb_breaking_onset` (new operator-adjustable config key, `[surf] qb_breaking_onset`, default 0.05 = today's unchanged `Q_B_VISIBLE` value) publishes its own marker, subject to a 30% topographic-prominence rule (`_BREAK_PROMINENCE_FRACTION`, pinned, not configurable) — independent of whether Q_b later falls below cessation anywhere in the region. The published impact zone becomes a fixed-width crash band per marker (new config key `[surf] impact_zone_width_m`, default 25.0 m, CONFIRMED by operator 2026-08-10), shoreward from the marker, clipped at the waterline; `foamZone` becomes pure geometry (shoreward edge of the most shoreward band to the waterline, no roller-energy term); `reformTrough` serves null. `Q_B_CESSATION`, the roller-energy reservoir, and INVARIANT_11's closure check remain internal-only physics state, entirely untouched.

> **WC-D3 surf height range.** The surf endpoint reports `modelSurfHeightMin` and `modelSurfHeightMax` — the smallest and largest per-partition face heights across the main break zone's qualifying transects (the 0.75σ best-surf selection, not a whole-beach average). Only qualifying partitions (Tp ≥ 5s) on qualifying transects contribute. `breakingFaceHeight` is redefined as `modelSurfHeightMax` (was the BD-7 main-zone headline); `waveHeightAtBreak` and `breakingHawaiianHeight` continue using the prior computation. When zero qualifying partitions have break data, all three are null. **P13 card-aggregate fields (LIVE 2026-08-09, L1-BOUNDARY-REBUILD-PLAN Phase C):** the endpoint additionally serves `swellHeightMinFt`/`MaxFt` (min/max deep-water swell height across eligible components, server-computed), `faceHeightMinFt`/`MaxFt` (min/max per-swell breaking face height over the same eligible components), and `combinedPeriodS` (energy-weighted mean period, `Hs_i²` weights). **`(ruled 2026-08-10; lands with Phase S of MARINE-PAGE-FIXIT-PLAN)` — target state (ADR-106 R2, PA2) supersedes `faceHeightMinFt`/`MaxFt` and `combinedPeriodS` above.** Operator ruling, verbatim: *"the period should never be combining periods, that is not how the physics works."* Target: `combinedPeriodS` is REMOVED; new fields `periodMinS`/`periodMaxS` (lowest/highest peak period across the eligible surfable swells) replace it. `faceHeightMinFt`/`MaxFt` are also REMOVED — the Swell Card's Breaking Face Height rebinds instead to `modelSurfHeightMin`/`modelSurfHeightMax` above (the best-surf-strip pair this section already documents), which is the field the operator's original Breaking Face Height definition actually describes. `swellHeightMinFt`/`MaxFt` are UNCHANGED by this ruling.

> **WC-D2 minimum surfable period floor (5 seconds).** Swell partitions with peak period Tp < 5.0 s are skipped before entering SwellTrack (`_MIN_SURFABLE_PERIOD_S`, `services/surf_1d_pipeline.py`) — sub-5s energy is wind chop, not surfable at any break type. This gates SwellTrack ONLY: SWAN processes all frequencies (correct physics requires the full spectrum), and the surf scorer still sees all partitions via the `spectral_dwr` channel (chop degrades the conditions score). Design constant, not admin config.

> **SwellTrack — proprietary analytical 1D cross-shore wave transformation model.** Runs per-transect from the SWAN handoff depth to shore **and up the beach face to the Highest Astronomical Tide (HAT)** — see the landward-boundary note below. **The cached bathymetric profile is truncated at that transect's per-hour handoff depth before the model runs** (marine `7fb75f9`) — SwellTrack takes its shoaling reference from the first point of the profile it is handed, so running it on the full transect re-shoaled water SWAN had already carried and applied the handoff-to-shore gain twice. Truncation is on the raw, untided profile depth (matching the upstream handoff selection) and snaps shoreward to an existing sample; a profile that cannot be truncated there is skipped with a WARNING, never run untruncated.
>
> **1D model LANDWARD boundary — `E_landward = HAT`, sized once at setup (ADR-093 Amendment 4, TA-C18).** The 1D model's *landward* end is the Highest Astronomical Tide contour, not the still-water shoreline. This is the symmetric complement of Amendment 2's seaward rule ("size to reach as far shoreward as it is *ever* useful"): size the profile to reach as far *landward* as it is ever useful for a surfable tide — the beach face up to HAT — so the moving shoreline stays inside the domain at every tide and a real wave always has wet ground to break on. **`E_landward = HAT` exactly — no storm-surge term, no wave/runup term** (this is a surf model, not a flood model). Three coupled changes in `services/grid_sizing_chain.py` + `enrichment/bathymetry.py`: **(1) each 1D transect finds its OWN true shoreline** (`find_shoreline_from_grid()`, elevation crosses 0 along the transect's own bearing) instead of anchoring at the SWAN POINTS-band origin (`_band_ray_origin`, ~1 m seaward of the waterline) — the 1D model is independent of SWAN except at the handoff; **(2) the per-transect profile is sampled with SIGNED subaerial depth** (`_grid_signed_depth_below_msl()`: land kept as NEGATIVE depth, not clamped to 0) and **extended landward up the beach face** at native spacing until seabed elevation reaches HAT or grid coverage ends (`extract_native_profile_from_grid(signed_subaerial=True, e_landward_m=…)`). **Distances are re-based so `distance_from_shore = 0` is the TRUE WATERLINE (the interpolated depth-0 crossing) — beach-face points landward of it are NEGATIVE, underwater points POSITIVE.** This keeps a break's reported `distanceFromShore` (which flows through `Analytical1DResult.distances` to the API) identical whether or not the transect was extended, since breaks are always seaward of the waterline; **(3) HAT is computed ONCE at setup** as the maximum of the SAME CO-OPS harmonic predictions feeding `tide_level` — a ≥1-year `interval=hilo` window for the spot's **LOCATION's** `coops_station_ids[0]` (the station lives on `MarineLocation`, not the surf-spot sub-config — the same source SWAN's runtime tide fetch uses), requested in the DEM's own datum (match-at-source, ADR-098) — stored in the per-spot profile cache as `e_landward_m`/`hat_m`/`hat_station_id`/`hat_datum`. `run_1d_analytical`'s existing `depth = max(seabed + tide, 0.01)` clamp then wets/dries the new beach-face cells per forecast hour automatically — no per-hour geometry change, grid geometry stays frozen at setup. **The per-spot PCHIP `profile` (which feeds `interpolate_profile_pchip()` and L4 SWAN-grid sizing) is UNCHANGED** — PCHIP rejects negative depths by contract and SWAN grid geometry is out of scope; only the per-transect 1D profiles (`profiles_by_transect`, which take priority in SwellTrack) carry the subaerial beach. On HAT-fetch failure, or a transect whose topobathy cannot reach HAT, the chain logs a WARNING and degrades (no landward extension) rather than aborting. Provides Hs at 3-5m CUDEM resolution, break points, breaker classification, wave shapes, surf zone widths, jacking factor, and peel angle. Bottom friction enabled by default (cfjon=0.038 for swell, 0.067 for windsea). Always runs in-process or via compute offloading — not a separate network service. Module: `services/surf_1d_analytical.py`.

> **Remote-mode data flow — publish results, not working data (SURF-PUBLISH-RESULTS-ONLY, 2026-07-25).** The SWAN service's `GET /surf/{spot_id}/forecast` serves a **trimmed published view**: four heavy per-timestep `spectral` fields (`energy`, `freqs_hz`, `dirs_deg`, `handoff_by_transect`) are dropped at the HTTP-serving boundary only (`weewx_clearskies_swan/service.py` `_trim_published_view()`). **librewxr's internal `_forecast_cache` and its on-disk `forecast_cache.json` keep the full working data, with one exception** (M-0/D-1b, SURF-PHYSICS-REMODEL-PLAN-2026-08-05, M0-D1B fact-pin: cached `spectral` entries are trimmed of the `freqs_hz`/`dirs_deg`/`energy` 2-D arrays — top-level and per-transect — since no live reader of that cache anywhere touches them; this is the class of unbounded-payload growth that OOM-killed the service) — the model host needs its own working data to answer profile requests (below), including after a restart; the model's own computation is unchanged. Measured 2026-07-25: actual wire bytes for one spot were 21,029,707 (~20.05 MB) pre-trim, ~2.4 MB expected post-trim — this is the wire figure that matters operationally. Separately, a `json.dumps` re-serialization of the same live payload measured 22.87 MB → 2.78 MB before/after the trim (the acceptance-criterion check, <3.5 MB — cited here as a re-serialization figure, not a wire measurement). The API (`providers/nearshore/swan.py` `_remote_health_loop()`) also stopped re-fetching this payload every 60 seconds regardless of content — it now compares the `GET /health` response's `last_run` against the `run_time` already in its local last-good cache and skips the forecast download when they match (a missing cache entry always fetches; the last-good cache has a 7-day TTL). The 60-second `GET /health` poll itself is unchanged. Combined effect: ~21 MB every 60 s → ~2.4 MB roughly once per ~25-minute model cycle for one spot — the payload cut and the cadence cut both apply, not one or the other.

> ### The marine service is an add-on reached only through the API — INVARIANT
>
> **Operator ruling, 2026-07-25. This is not a preference and it is not negotiable.**
>
> The marine service is an **add-on to the API**. It does **not** necessarily live on the same host.
> Therefore **every other element of Clear Skies communicates with it through the API, and only
> through the API** — the dashboard, the config UI wizard, the admin pages, and any third-party
> client alike. This holds for **security** (one authenticated boundary, one secret, one place where
> auth and rate limiting are enforced) and for **coordination** (one source of truth for operator
> config, one place that knows whether the service is even installed).
>
> Concretely:
>
> | Component | Talks to the marine service |
> |---|---|
> | Dashboard | **No.** Calls the API's `/api/v1/*` routes, which the companion proxy mounts. |
> | Config UI / wizard | **No.** Calls API endpoints. Where the wizard needs marine data — nearby buoy or tide stations, the covering OFS model, GRIB availability — the API **proxies** the query to the marine service, which exposes them as `GET /discovery/{buoy-stations,tide-stations,ofs-model,grib-availability}` (C-42, DECIDED, implemented) — bearer-authenticated, each an exact pass-through of the underlying provider function's own return shape, registered in the marine service's `GET /manifest` (C-30's lesson applied: a route not in the manifest is invisible to the API). Two more `GET /discovery/{compute-estimate,bathymetry-coverage}` endpoints (C-48, DECIDED, implemented) cover the wizard's before/after compute-cost display and bathymetry-coverage panel — the former `/setup/marine/compute-estimate` and `/setup/marine/coverage` bathymetry block, now proxied the same way. These two run the grid-sizing and DEM-index physics inside the marine service rather than passing through a single provider function unchanged, since no single provider function produced either shape even before the move. A fourth, `GET /discovery/swan-check` (C-54, DECIDED, implemented), answers whether the SWAN binary is installed and reports the host's CPU core count — this has to run on the marine service host specifically, since that is the host that actually runs SWAN; the API's former local `shutil.which("swan")` check answered the question about the wrong host entirely. |
> | Admin pages | **No.** Same as the wizard. |
> | Any third-party client | **No.** |
> | The API | **Yes — the only one.** |
>
> **The corollary that keeps getting missed:** when the API needs marine data for something that is
> not a dashboard route — a wizard lookup, a setup-time question, an operational check — the answer is
> a **pass-through in the API**, never a marine provider module imported into the API and never a
> direct call from another component. If a new need arises, the shape is always the same: the marine
> service exposes it, the manifest or an explicit proxy route carries it, the API fronts it.
>
> **Why this is written down (2026-07-25):** during Phase 6 the coordinator twice proposed
> alternatives that violated it — keeping marine provider modules in the API "because the wizard needs
> them", and having the wizard call the marine service directly. Both were rejected. The invariant was
> implicit in ADR-099 and in the companion-proxy design but was never stated as a rule, so each new
> case was re-argued from scratch.

> **Manifest registration pattern.** The marine service exposes `GET /manifest` (no auth) returning a JSON endpoint manifest listing all marine endpoints with their upstream paths, HTTP methods, and cache TTLs. At API startup, the companion proxy (`services/companion_proxy.py`) fetches the manifest and dynamically registers routes under `/api/v1/`. The manifest refreshes every 5 minutes — endpoint additions take effect without an API restart. Removing an endpoint from the manifest de-registers its route on the next refresh. Adding a new marine endpoint to the marine service requires zero API code changes. When `marine_service_url` is not configured, no marine routes are mounted and marine capabilities are absent from `GET /api/v1/capabilities`.
>
> **Marine service environment (Phase 4).** `MARINE_SERVICE_SECRET` (required, no default — process refuses to start if unset; a request while unset returns 500, deliberately distinct from a client's 401). `CLEARSKIES_MARINE_CACHE_URL` (optional; unset = in-process memory cache) — **distinct from the API's `CLEARSKIES_CACHE_URL`** because same-host deployment is supported and a shared Redis database would collide the two services' key namespaces. `CLEARSKIES_MARINE_BIND_HOST` (default `0.0.0.0`, mirrors the API's `CLEARSKIES_BIND_HOST`). Files under `/etc/weewx-clearskies/marine/`: `secrets.env`, `marine.conf` (atomic write, mode 0640), `marine-cert.pem` / `marine-key.pem` (Ed25519 self-signed, key mode 0600). CLI: `--host`, `--port`, `--cert-dir`, `--hostname`, `--config`. Request bodies capped at 1 MiB (413 problem+json), matching the API — `POST /config` persists next to the TLS private key, so an unbounded body is a disk-fill vector. See OPERATIONS-MANUAL "Marine service environment and paths".
>
> **Configuration.** Operator sets `marine_service_url = https://{host}:8780` in `api.conf [providers]`. Deployment options: same-host (`https://localhost:8780`) or separate-host (e.g., `https://192.168.7.22:8780` or `https://[fd12:3456:789a::1]:8780`). `MARINE_SERVICE_SECRET` (Bearer token) in `secrets.env` authenticates all requests except `GET /health` and `GET /manifest`. Config push: on wizard/admin apply, the API's `/setup/apply` handler POSTs marine configuration to `{marine_service_url}/config` (authenticated). The marine service never reads `api.conf` — the API is the single source of truth for operator config.
>
> **Runtime failure handling.** If the marine service is unreachable at API startup, the API logs an error and starts without marine routes; it retries every 5 minutes. If the marine service becomes unreachable after startup, mounted routes return the last cached response (`freshness.validUntil` in the past — stale data preferred over no data). If no cache exists for a route, the API returns 503 with a structured error.
>
> **Alerts stay in the API.** Marine alerts (coastal flood advisory, high surf advisory, rip current statement) are served by the API's unified NWS alert system (`providers/alerts/nws.py`). They are never moved to the marine service, regardless of whether the marine service is installed or configured. This is unconditional.
>
> **API footprint.** With the marine service installed, the API contains zero marine physics code, zero marine provider modules, and zero hardcoded marine routes. The generic companion proxy module (`services/companion_proxy.py`) handles manifest fetch, route registration, and response envelope wrapping/unit conversion for proxied responses. All marine physics and provider logic is in the marine service repo.

Schedule: top-up poll every 5 min during a cycle's upload window (cycle start +50 min to +2 h, or until complete), idle poll every 15 min otherwise, cold-start reconciliation against the store on startup. Reuses `hrrr.py`'s/`gfs.py`'s own per-forecast-hour building blocks (URL construction, GRIB2 extraction, Lambert rotation, cycle-time arithmetic) as-is via its own fetch seam (`_fetch_one_hrrr_hour()`/`_fetch_one_gfs_hour()`) — those modules are not modified. Runs its own `RateLimiter` at hrrr.py's/gfs.py's full 2 req/s NOMADS policy (restored at Z3.5 once it became the sole routine caller — it ran at half that policy during migration steps 1-4, when the run loop's own inline fetch was still a concurrent NOMADS caller).
>
> **The wind timeline store (`services/wind_timeline_store.py`).** ONE assembled wind timeline, updated in place — not per-cycle fragments. `wind_timeline.json(.gz)`: one record per forecast hour over the working window (now → +72h), each carrying the grid data + per-hour provenance (source cycle, issue time, fetched-at); a fresher cycle's hour REPLACES the existing one in place. `incoming.json`: completeness tracker for the cycle currently being assembled, cleared on completion. Read API: `get_wind_series(t0, t1)` (uniform-hourly contract; refuses with a named reason — `WindSeriesGapError` — on any gap, by construction never silently interpolates across one) and the regime-aware `get_wind_records(t0, t1)` (native HRRR-hourly 0-48h, native GFS-3-hourly 48-72h, used by the SWAN run triggers below since a single uniform-hourly contract cannot represent the far window's native cadence) and `get_status()` (freshness/completeness summary, consumed by `GET /health`'s additive `windGatherer` key).
>
> **Consumers, all read-only against the store, all switched over by migration step 5 (Z3.5):**
> - **Full 48h SWAN run:** triggered BY `extended_cycle_assembled` (~4×/day) via `providers/nearshore/swan.py`'s `run_full_swan_cycle_from_store()`; reads `get_wind_records()` over the run's own 0-72h window. A `force_full_run_signal` (geometry-changing config push) converges on the SAME function, forced, dedup-bypassed.
> - **Hourly fast cycle:** triggered BY `hourly_cycle_assembled` via `run_quick_update_from_store()`; 12 forecast hours (operator: "half a day"), window anchored to the event's own cycle_time. No forced-bypass analog — fires ONLY on assembled-complete.
> - **Surf-card display wind:** `endpoints/surf.py` reads `get_present_hours()` — a tolerant sibling of `get_wind_series()` that NEVER refuses on a gap, returning whatever hours of the requested range are actually present — at request time, one in-process, file-backed read per request, never a fetch. The store is PRIMARY for every hour it returns; `wind_for_display` (the run-forced spot-pin wind field, sampled once per forecast hour during the SWAN run itself, unchanged from its pre-migration build) is the PERMANENT fallback for every hour the store does not cover — aged-out past hours, 3-hourly far-window off-slot hours, or a store-absent/cold read. Both sources absent for an hour → null, never a fabricated value. This is a permanent hybrid (Q3 ruling, 2026-08-11), not a transition: the store's own self-bounding design (`age_out()` at wall-clock now + native 3-hourly far window) means it can never cover the served timeline's full range by construction. A single WARNING fires only when the store returns zero hours in range while the gatherer is enabled (store dead/cold — genuinely anomalous); the request-time HRRR fetch and the H5 publish-time warming thread this replaced remain deleted.
> - **`GET /health`'s `inputs.wind` freshness signal:** recorded by `run_full_swan_cycle_from_store()`/`run_quick_update_from_store()` themselves, right after their own store read (`state.record_input("wind", ...)`) — the run loop's own inline-fetch bookkeeping that used to record this is deleted along with the fetch itself.
>
> Both run triggers are event-driven ONLY as of migration step 5 — `_marine_runner_loop()` carries no inline HRRR/GFS fetch, no cycle-cadence classification, and no cycle-change bookkeeping of its own; it only consumes the gatherer's two events (plus the forced-geometry-push signal for the full run) on its existing `check_interval_s` (300s) tick.
>
> **Trigger lifecycle hardening (Z3.9b, 2026-08-13, audit findings V6–V13).** Both pending triggers retry until success (peek, CAS-clear-on-success — the full-run trigger since Z3.6/D3, the hourly trigger since Z3.9b). The full run additionally carries a consecutive-failure counter: after 3 failures of the SAME cycle the retry cadence backs off from every tick to every 30 min, and `GET /health` exposes a `fullRun` block (last success cycle/time, pending cycle, consecutive failures, last failure reason) with an `overdue` flag — overdue + ≥3 failures moves health to a distinct "degraded" status, so a permanently-failing full run can no longer look healthy. Run-gating state survives restarts via three small persisted files beside the wind timeline (atomic temp+replace, all under the SWAN work root): `state_snapshot.json` (input-freshness registry + full-run record, restored with ORIGINAL timestamps — ages stay honest), `run_markers.json` (6h-TTL full-run dedup markers, disk shadow of the in-process cache), and `force_full_run.flag` (a set-but-unconsumed forced-run signal, re-armed on startup). On startup the runner also cold-start reconciles: an assembled extended cycle with no completed run marker re-arms the pending full-run trigger, so a deploy/restart no longer silently drops a pending run. The forced path sources its cycle from the gatherer's restart-safe `tracks.hrrr_extended.lastCompleted`, not the in-memory events field. The far-window store read geometry-homogenizes mixed-provenance grids onto the GFS grid before stitching (Z3.7, operator option-2 ruling — see PROVIDER-MANUAL).

> **Config UI containerization (resolved 2026-07-02).** The Config UI has a Dockerfile (multi-stage, two-repo build context) and is included as the `config` service in `frontend-host/` and `single-host/` compose files. Caddy proxies `/wizard*`, `/bootstrap*`, `/login*`, `/admin*`, `/static/*` to the config service on port 9876. It is also distributed as a pip package (`weewx-clearskies-config`) for native installs.

> **API native install (2026-05-24):** The API is currently installed natively on the `weewx` LXD container (not in Docker) via pip into a Python 3.12 venv at `/home/ubuntu/repos/weewx-clearskies-api/.venv`, managed by systemd unit `weewx-clearskies-api.service`. Config at `/etc/weewx-clearskies/api.conf`. Health port (8081) also serves TLS. This is the production deployment path on bare-metal / LXD; the Dockerfile exists for Docker compose deployments.
>
> **API startup time: ~2 minutes.** After `systemctl restart weewx-clearskies-api`, the service runs a cache warmer that makes outbound API calls to configured providers (Vaisala Xweather, NWS, etc.) before uvicorn binds to port 8765. The warmer pre-populates the cache for all slow endpoints: `/forecast` (30-min TTL), `/current` conditions blend (5-min TTL), almanac, records, earthquakes/faults, seeing forecast, and marine provider data. `/forecast` and `/current` are the two slowest cold calls (11s and 6.2s respectively) — the warmer ensures visitors never hit these cold paths. The service is not ready to serve requests until the initial cache warm completes. When scripting restarts, wait at least 120 seconds before hitting endpoints — `sleep 10` is not enough.

> **Native dashboard / dev deploy (2026-05-29):** On the `weather-dev` LXD container the dashboard is NOT run as a Docker init container. Instead the source is pulled to `/home/ubuntu/repos/weewx-clearskies-dashboard`, built natively with `npm run build` (Vite → `dist/`), and the built `dist/` is rsync'd into the Caddy web root `/var/www/clearskies/` (excluding the read-only `webcam/` bind-mount and the `cards/` directory). API and Config UI run as systemd units (`weewx-clearskies-{api,config}.service`). The full redeploy is automated by `scripts/redeploy-weather-dev.sh`; source-only refresh by `scripts/sync-to-weather-dev.sh`. Procedure: [procedures/deploy-clearskies.md](procedures/deploy-clearskies.md). The Docker init-container model above is the compose deployment path.
>
> **Cards directory (v2 prep, ADR-064):** `/var/www/clearskies/cards/` is reserved for third-party card assets (v2 scope). The redeploy script excludes this directory from rsync (`--exclude cards/`), same isolation pattern as `webcam/`. Empty until v2 adds the card import mechanism. Caddy serves `/cards/*` from this directory.

Current SoCal BBOX is entirely within GOES-18 — zero impact.

**Single-host alternative:** All services on one machine. Caddy proxies to local Docker network name `api:8765` for both `/api/v1/*` and `/sse`. API uses direct mode (Unix socket to weewx engine).

## Caddy routing

All three Caddyfile variants (frontend-host, single-host, examples/reverse-proxy) route both `/api/v1/*` and `/sse` directly to the API at port 8765. There is no intermediate proxy — the API serves both REST and SSE directly (ADR-058). When the operator configures LibreWxR as the radar provider, the wizard adds a `/librewxr/*` reverse proxy route pointing at the LibreWxR instance (public API or self-hosted). This route strips the `/librewxr` prefix before forwarding. LibreWxR is an external service — not a Clear Skies container.

## Webcam

The webcam feature is a UI concern. The API has no webcam knowledge.

### File serving

An external capture process writes two files to the weewx LXD container at `/var/www/weewx/webcam/`:

- `weather_cam.jpg` — live still image
- `weewx_timelapse.mp4` — timelapse video

An LXD disk device mounts the host path `/mnt/weewx/webcam` read-only into the `weather-dev` container at `/var/www/clearskies/webcam/`. Caddy serves the `/webcam/*` path via `file_server` from that directory with no `try_files` fallback — a request for a missing file returns 404 immediately.

### Configuration flow

The setup wizard (stack repo) collects webcam settings: enabled flag, image URL, video URL, and refresh interval. On apply (`/wizard/apply`), the wizard writes two outputs:

| Output | Path | Purpose |
|--------|------|---------|
| `webcam.json` | `/etc/weewx-clearskies/webcam.json` | Static JSON fetched directly by the dashboard; contains `enabled`, `imageUrl`, `videoUrl`, `refreshInterval`. Served by Caddy at `/webcam.json` from `/etc/weewx-clearskies/` — outside the web root so dashboard rsync --delete cannot remove it. |
| `[webcam]` section | `stack.conf` | Persists settings so the wizard can pre-fill them on re-run |

The dashboard fetches `/webcam.json` on the Now page. If `enabled` is true, it renders the webcam card. If the fetch fails or `enabled` is false, the card is hidden gracefully — no error state surfaced to the user.

### Data flow

```
External capture process
  → /mnt/weewx/webcam/ (host path on weewx container)
  → LXD disk device (read-only mount)
  → /var/www/clearskies/webcam/ (weather-dev container)
  → Caddy file_server (/webcam/*)
  → browser

Wizard step 7 (apply)
  → /etc/weewx-clearskies/webcam.json  (dashboard config; safe from rsync)
  → stack.conf [webcam]                (wizard re-run pre-fill)
  → Caddy /webcam.json route → file_server from /etc/weewx-clearskies/
  → Dashboard fetches /webcam.json on Now page load
  → renders webcam card if enabled, hides gracefully on error
```

### API response envelope (ADR-075)

All cacheable API endpoints return a standard response shape. Non-cacheable responses (SSE events, setup endpoints) omit the `freshness` block.

```json
{
  "data": { ... },
  "stationClock": {
    "date": "2026-06-27",
    "time": "2026-06-27T22:30:00-04:00",
    "timezone": "America/New_York"
  },
  "freshness": {
    "generatedAt": "2026-06-28T02:30:00Z",
    "validUntil": "2026-06-28T03:00:00Z",
    "refreshInterval": 1800
  },
  "units": { ... },
  "generatedAt": "2026-06-28T02:30:00Z"
}
```

**`stationClock`** — present on ALL API responses. The station's current local date and time, computed at response time from the configured station timezone. No database query required. Fields:
- `date` — station-local date as YYYY-MM-DD. Canonical answer to "what day is it at the station?" The dashboard uses this for all date-boundary logic (forecast "Today" labeling, almanac day transitions, etc.).
- `time` — station-local time as ISO-8601 with UTC offset. The UTC offset is included so the dashboard can convert to epoch ms for elapsed-time math without a timezone library.
- `timezone` — IANA identifier (e.g., `"America/New_York"`).

The station clock timezone authority chain (highest to lowest priority):

| Priority | Source | When used |
|----------|--------|-----------|
| 1 | Operator setting in `api.conf` or wizard | Always preferred when set |
| 2 | weewx.conf `[Station] timezone` | Auto-detected at startup |
| 3 | OS timezone of the weewx host | Fallback when weewx.conf has no timezone |
| 4 | UTC + startup warning | Last resort; operator must configure |

**`freshness`** — present on cacheable responses ONLY. Not present on SSE events or setup endpoints. Fields:
- `generatedAt` — UTC ISO-8601 Z timestamp when the API produced this response.
- `validUntil` — UTC ISO-8601 Z timestamp after which the data should be considered stale. The dashboard schedules background refetches when `Date.now() > validUntilMs`.
- `refreshInterval` — integer seconds. How often this data type typically updates at the source. Cards use this as a proactive poll timer.

Per-domain `refreshInterval` defaults are configured in `api.conf [freshness]` (see Configuration files below). The `current_observation` and `records` domains derive their default from `archive_interval` (see weewx configuration ingestion below).

**`data`** — the response-specific payload (observation, forecast, alerts, etc.).

**`units`** — unit labels for all numeric fields (existing; unchanged by ADR-075).

**`generatedAt`** — UTC timestamp of response generation (existing top-level field; also mirrored inside `freshness.generatedAt` on cacheable responses).

### Conditions text engine (ADR-073)

The API hosts a multi-module, stateful conditions-text engine that produces the `weatherText` field on every `GET /api/v1/current` response. (Formerly in the realtime service; merged into the API per ADR-058.)

| Module | Role |
|--------|------|
| `weewx_clearskies_api/sse/sky_condition.py` | Stateful classifier — Kv-first (Duchon-O'Malley architecture with SkyPyEye Technology indices), 30-min ring buffer of 1-min GHI averages, mean-of-ratios Km, elevation-dependent dynamic thresholds, produces the sky label |
| `weewx_clearskies_api/sse/temperature_comfort.py` | Stateless 2D matrix — maps (appTemp, dewpoint) to comfort label |
| `weewx_clearskies_api/sse/enrichment/weather_text.py` | Enrichment adapter — reads smoothed inputs + sky class, calls `build_weather_text()`, injects result into the `/current` response dict. Provider cross-check for fog/mist confirmation. |
| `weewx_clearskies_api/sse/haze_condition.py` | Haze detection — two-channel (Kcs deficit below dynamic clear threshold from `sky_condition.get_dynamic_clear_threshold()` + RH-graduated PM confirmation: PM2.5 50/35/25, PM10 100/75/50 µg/m³ at dry/moderate/humid RH), solar elevation gate (el > 15°), f(RH) correction, 5-min coherence |
| `weewx_clearskies_api/sse/observation_model.py` | Structured local observation model — METAR-like field mapping |
| `weewx_clearskies_api/sse/conditions_text.py` | Current-conditions composer — assembles the `weatherText` string from per-component labels. **Known limitation:** wind labels/gust phrasing now delegate to the GFE hybrid wind scale (ADR-082); sky, comfort, and precipitation composition are unchanged pending the current-conditions upgrade — see §15 preservation directive in API-MANUAL.md |
| `weewx_clearskies_api/sse/text_generation.py` | NWS-style text engine — terse/standard/verbose verbosity for current conditions, GFE threshold tables. **Known limitation:** superseded by `sse/gfe/` for forecast-period text (ADR-082); still active for current-conditions verbosity tiers pending the current-conditions upgrade |
| `weewx_clearskies_api/sse/gfe/composer.py` | GFE forecast text composition — single-pass sequential assembly of period narratives (ADR-082) |
| `weewx_clearskies_api/sse/gfe/thresholds.py` | GFE threshold tables — sky, temperature, wind, weather, PoP, snow/ice, marine, fire (ADR-082) |
| `weewx_clearskies_api/sse/gfe/*.py` | GFE phrase generators — sky, temperature, wind, weather/precip, snow/ice, marine, fire, time descriptors, connectors (ADR-082); see API-MANUAL.md §15 Module inventory for the full file list |
| `weewx_clearskies_api/sse/forecast_model.py` | `ForecastPeriod` dataclass — aggregated per-period input consumed by the GFE composer (ADR-082) |
| `weewx_clearskies_api/sse/period_aggregator.py` | Aggregates 72 hourly forecast points into 6 day/night `ForecastPeriod` instances (ADR-082) |
| `weewx_clearskies_api/sse/forecast_text_enrichment.py` | Enrichment adapter for `/api/v1/forecast` — populates `DailyForecastPoint.forecastText` (ADR-082) |

**AQI data flow:** PM2.5/PM10 from observed-data AQI providers (Vaisala Xweather, IQAir) flow through the enrichment pipeline via new 60-minute smoothing buffers in `input_smoother.py`. Smoothed PM values feed the haze detection module and fog/mist disambiguation. Model-based AQI providers (Open-Meteo) are excluded from haze confirmation. At night (solar elevation at or below the 15° detection gate), haze/smoke defers to provider current conditions observations; fog/mist remains local.

**New response fields on `/api/v1/current`:** `weatherTextStandard` (NWS one-sentence format) and `weatherTextVerbose` (full narrative). `weatherText` continues to carry terse format (backward compatible).

**Inputs:** smoothed loop-packet fields via `enrichment/input_smoother.py` — `rainRate` (2 min), `windSpeed`/`windGust` (5 min), `appTemp`/`dewpoint`/`outTemp`/`heatindex`/`windchill` (10 min), `radiation`+`maxSolarRad` (30 min kc rolling window). No database access.

**Output:** `data["data"]["weatherText"]` on the `/current` JSON response — a composed natural-language string (e.g., `"Warm and Humid, Partly Cloudy, with Light Rain"`) or `null` when no components are available.

**Transport:** REST only. `weatherText` is NOT included in the SSE loop-packet field map (`WEEWX_TO_OBSERVATION`) and is NOT updated via SSE. The conditions sentence updates at the REST poll interval, not at loop-packet frequency.

**Registration:** The API's `__main__.py` registers `enrich_weather_text` against the `"current"` endpoint key. Every `GET /api/v1/current` response is enriched before being returned to the browser.

**Sky classification (ADR-073):** Kv-first decision tree in the Duchon & O'Malley (1999) tradition — variability-primary, clearness-secondary — using SkyPyEye Technology indices (adapted from CAELUS research library; Ruiz-Arias & Gueymard 2023). Four indices (Kcs, Km, Kv, Kvf) computed from 1-minute GHI averages over a 30-minute ring buffer. **Km** is computed as the mean of per-minute ratios: (1/n) Σ(GHI_i / maxSolarRad_i) — not ratio of integrals. Kv and Kvf are **clear-sky-detrended**: each minute-to-minute GHI change has the corresponding maxSolarRad change subtracted, isolating cloud-induced variability from deterministic solar geometry (Stein et al. 2012, Sandia Variability Index). Primary axis: Kv distinguishes uniform sky (Kv < 0.05: clear or overcast) from variable sky (Kv ≥ 0.05: broken coverage). Within uniform and variable branches, Km is compared against **elevation-dependent dynamic thresholds** computed by `get_dynamic_clear_threshold(α) = K_min + (K_max − K_min) · (1 − e^(−b · α))` — fixed constants cannot work across all solar elevations (Smith, Bright & Crook 2017). Cloud enhancement (Kcs > 1.06 + high Kv + high Kvf) → "Partly Cloudy" (broken-cloud scenario, not clear-sky). Seven labels total: Clear, Mostly Clear, Partly Cloudy, Mostly Cloudy, Cloudy, Overcast, Heavy Overcast. Temporal coherence filter (5-min persistence). Startup backfill from archive records. **GHI mirroring** across sunrise/sunset boundaries via cos(zenith) interpolation (adapted from CAELUS library's `sky_indices.py`), stabilizing Km at low solar elevations. **SZA < 75° guard**: `classify()` returns None when solar elevation < 15°, falling back to provider cloud cover. Solar elevation computed via Skyfield from station coordinates. Full scientific citations in `docs/reference/sky-classification-science.md`.

**Startup behavior:** On API restart, `backfill()` seeds the sky classifier's ring buffer from archive records (last 30 minutes), enabling immediate classification. The temporal coherence filter applies a 3-minute startup grace. Full SkyPyEye-quality classification after ~30 minutes of live LOOP data. When solar analysis is unavailable (night, twilight, no pyranometer, or SZA guard engaged at elevation < 15°), the engine falls back to provider cloud cover via `_cloud_pct_to_sky()` in `enrichment/weather_text.py`, which maps cloud cover percentage to the sky label with day/night vocabulary awareness.

## Unit conversion (ADR-042, updated for ADR-058)

The API converts all outbound data (both REST responses and SSE events) from the source unit system to the operator's configured display units. The dashboard receives `{value, label, formatted}` objects and has zero unit knowledge.

**REST path:** API queries archive values with `usUnits` declaring the unit system → looks up each field's group → converts to operator display unit → attaches label and formatted string.

**SSE path:** Direct adapter delivers loop packets with weewx unit system → API strips any unit suffixes → identifies source unit → converts to display unit → attaches label.

**Derived values:** Beaufort scale and comfort index (wind chill vs heat index) computed by the API's enrichment pipeline. Dashboard does not carry thresholds.

**Config:** `api.conf` `[units]` section (formerly `realtime.conf`) — `[[groups]]` (display unit per group), `[[string_formats]]` (decimal places), `[[labels]]` (display symbols), `[[ordinates]]` (compass directions), `[[time_formats]]`, `[[degree_days]]`, `[[trend]]`. Mirrors weewx skin.conf `[Units]` subsection names. Supports all 14 weewx unit groups.

## weewx configuration ingestion

The API reads operator-specific parameters from weewx.conf at startup and exposes them to all consumers. These values are NOT hardcoded — they vary per installation.

| weewx.conf section | Key | `StationInfo` field | `/station` field | Default | Purpose |
|---|---|---|---|---|---|
| `[StdArchive]` | `archive_interval` | `archive_interval` | `archiveIntervalSeconds` | 300 | Archive record cadence in seconds. Drives chart proportional scaling, sky classifier freshness (`is_daytime()` threshold = 5× interval), temperature comfort hold time (5× interval), and barometer trend grace. |
| `[Station]` | `week_start` | `week_start` | `weekStartDay` | 6 (Sunday) | First day of calendar week (0=Monday, 6=Sunday). Dashboard uses it for `time_length = week` chart groups to compute calendar-week boundaries instead of a rolling 7-day window. |

**Data flow:** `load_station_metadata()` in `services/station.py` reads both values from the parsed weewx.conf `ConfigObj` → stores on `StationInfo` → exposed via `GET /api/v1/station` as `archiveIntervalSeconds` and `weekStartDay` → consumed by the dashboard's `ConfigDrivenGroup` component for chart data fetching and proportional aggregate scaling.

**Enrichment wiring:** At startup, `__main__.py` passes `archive_interval` to `sky_condition.configure()`, `temperature_comfort.configure()`, and (as the default `trend_time_grace`) to `barometer_trend.configure()`.

**Temporal model wiring (ADR-075):** At startup, `archive_interval` also sets the default `refreshInterval` for the `current_observation` and `records` freshness domains. A station with `archive_interval = 60` refreshes current-observation at 60s; a station with `archive_interval = 900` refreshes at 900s. Operator override via `[freshness]` section in `api.conf`.

**Reference implementation:** Belchertown's `belchertown.py:370-376` reads `config_dict["StdArchive"]["archive_interval"]` and converts to milliseconds for the frontend. `belchertown.py:2548` reads `config_dict["Station"].get("week_start", 6)` for calendar-week span computation.

## Charts configuration

The charts system is operator-configurable via `charts.conf`, a ConfigObj/INI file (same format as weewx `skin.conf` — operator familiarity, per ADR-027). Three-level nesting: group → chart → series, matching Belchertown's `graphs.conf` structure.

**Data flow:** `charts.conf` is parsed by `services/charts_config.py` at API startup. Each series is pruned against the `ColumnRegistry` — series whose `observation_type` is not present in the database are removed, and empty charts/groups cascade-removed. The pruned config tree is served via `GET /api/v1/charts/config`. The dashboard's `ConfigDrivenGroup` and `ConfigDrivenChart` components fetch this config and render charts dynamically using Recharts (standard time-series) or custom SVG (wind rose, weather range).

**Proportional scaling (2026-06-07):** For rolling-range chart groups (1d/3d/7d/30d/90d), the dashboard computes a proportional `aggregate_interval` matching Belchertown's data-density approach: `ratio = max(1, range_seconds / base_time_seconds)`, `aggregate_interval = base_aggregate_interval × ratio`. This keeps ~170–288 data points per chart regardless of time range. The `aggregate_interval` (seconds) is passed to `GET /api/v1/archive` which groups records into `FLOOR(dateTime / N) * N` buckets.

**Per-field aggregation:** Each series in `charts.conf` may specify an `aggregate_type` (e.g., `sumcumulative` for cumulative rain, `max` for rainRate). The dashboard reads these from the chart config and passes them to the API as `agg_map=rain:sumcumulative,rainRate:max,...`. The API applies the specified SQL function per field within each proportional bucket; fields without an explicit type default to `AVG` (matching Belchertown's rolling-range default). The `sumcumulative` type applies `SUM` per bucket then accumulates the results into a running total — each record's value is the sum of all previous records. This replaces Belchertown's hardcoded `rainTotal` post-processing with an explicit, operator-configurable option that works for any observation.

**Grouped aggregation (`xAxis_groupby` charts):** Charts that group data by calendar period — such as Average Climate (monthly averages) — set `xAxis_groupby` in `charts.conf` and do NOT use `GET /api/v1/archive`. Instead the dashboard calls `GET /api/v1/archive/grouped` with `group_by=month|day|hour|year`. Series that need two-level aggregation (e.g., average of daily highs) specify both `aggregate_type` and `average_type` in `charts.conf`; the dashboard encodes these as `field:agg_type:avg_type` in the `fields` parameter (e.g., `outTemp:avg:max`). There is no `/climatology/*` endpoint; the former `/climatology/monthly` endpoint was removed and its use cases are fully covered by `/archive/grouped`.

**API archive conversion (2026-06-07, updated for ADR-058):** The API applies `UnitTransformer.transform_record()` to `/archive` responses. It infers `usUnits` from the response envelope's `units` label block (same as `/current`), converts each record, injects derived fields (`beaufort`, `comfortIndex`), and flattens ConvertedValue dicts to full-precision scalars. The `beaufort` field is kept as a `{value, label, formatted}` dict (not flattened) so the wind rose binning can read it via `extractNumber()`.

**Wind rose:** uses client-side binning from the API-injected `beaufort` field (per ADR-041 computation boundary amendment, ADR-042, ADR-058). The dashboard makes a **separate raw archive fetch** (no `aggregate_interval`) for wind rose data, with `fields=windSpeed,windDir` and a high limit. This preserves the actual wind speed distribution for correct Beaufort classification — aggregated (AVG'd) wind speeds would smooth out higher categories. The dashboard reads `beaufort.value` from these raw records and bins into a 16-direction × 7-Beaufort-speed matrix. No Beaufort computation in the dashboard — the API is the single Beaufort authority.

**Special series types:** The charts system recognizes three series names that trigger automatic rendering behavior — the dashboard switches chart component and data-fetching strategy without any additional operator config:

| Series name | Rendering | Data strategy | Automatic behaviors |
|-------------|-----------|---------------|---------------------|
| `windRose` | Custom SVG polar chart (16 directions × 7 Beaufort speed bands) | Separate raw (unaggregated) archive fetch for `windSpeed`+`windDir`; no `aggregate_interval` | Uses API-injected `beaufort` field for speed classification. Default Beaufort colors: `#7cb5ec, #b2df8a, #f7a35c, #8c6bb1, #dd3497, #e4d354, #268bd2`. Operator can override via `beauford0`–`beauford6` keys in `charts.conf`. |
| `weatherRange` | Recharts arearange (when `area_display = 1`) or columnrange (default). Polar only when `polar = true` is explicitly set. | Dual archive fetches: `agg=min` and `agg=max` with `aggregate_interval=86400` (daily) | JS applies 15-band temperature color zones (deep blue ≤0°F → red-orange ≤90°F → pink-red >110°F; Celsius equivalents for metric stations). Per Belchertown wiki: default is columnrange, NOT polar. |
| `haysChart` | Recharts arearange, `polar=true` (always — this is a circular 24-hour wind chart by design) | Queries `windSpeed` (max) and `windGust` (max) with auto-calculated `aggregate_interval` | Emulates Mount Washington Observatory circular wind chart: hour of day on circle, wind speed as radius. `yAxis_softMax` config controls radial scale. |

The system is fully config-driven: operators configure series names in `charts.conf`; the dashboard detects special names and switches chart components automatically. All other series render as standard Recharts time-series charts (line/spline/area/column/scatter).

**Weather range chart:** Recharts arearange or columnrange showing daily temperature range with 15-band color zones. Uses dual archive fetches (`agg=min` and `agg=max`) to get daily extremes. Renders as Cartesian chart by default; polar only when `polar = true` is explicitly set in `charts.conf`.

**Custom SQL queries:** operators define SQL in `charts.conf` (disk-only, same trust model as Belchertown). Queries are pre-validated at startup via `EXPLAIN`, executed in read-only transactions with a 10-second timeout and DDL keyword blocklist. Served via `GET /api/v1/charts/custom-query/{series_id}`.

**Migration:** `clearskies-migrate-charts` CLI converts Belchertown `graphs.conf` → Clear Skies `charts.conf`. Most INI keys are identical by design; the tool annotates unsupported keys with `# NOTE:` comments. The migration tool injects rendering defaults: `markerEnabled=false` on line/spline/area series, `type=scatter` promotion for `lineWidth=0` series (windDir), `yAxisTickDecimals=2` for barometer, `yAxis_min=0` for rain series.

## API TLS

The API always serves TLS (ADR-038 amendment to ADR-008):
- **Default:** Auto-generates Ed25519 keypair + self-signed X.509 cert on first start. Stored in config directory. Fingerprint (SHA-256) printed to terminal.
- **Override:** Operator supplies cert/key via `[tls] cert_path` / `key_path` in `api.conf` or `--tls-cert` / `--tls-key` CLI flags.
- **Trust handshake:** First-time setup: API prints address + trust token + fingerprint → operator enters in wizard step 1 → config UI verifies fingerprint + sends token → API validates, issues session → token consumed (single-use) → fingerprint pinned (SSH-style).

Each module: outbound API call → response parsing → canonical field translation → capability declaration → error handling. Keyed providers proxied server-side (keys never reach browser).

Four provider domains for marine/ocean data remain in the API: `"marine"` (wave forecasts and text), `"tides"` (predictions and water levels), `"buoy"` (point observations), `"ocean"` (water temperature profiles, currents, salinity from OFS coastal models and ERDDAP global datasets). `"wind"` (HRRR + GFS, Phase 7) and `"nearshore"` (SWAN runner, Phase 7) have moved to the marine service. All v1 remaining API marine/ocean provider modules are NOAA sources — free, keyless, US-only. See PROVIDER-MANUAL §14.

Ocean data is accessed through the `ocean_data_resolver` service (`services/ocean_data_resolver.py`) which implements a tiered fallback chain: on-premises sensor → OFS regional model → regional ERDDAP → RTOFS/MUR SST global → unavailable. Endpoints call `resolve()` instead of calling ocean providers directly.

**C-42 (2026-07-25, executed): the wizard's discovery helpers are API pass-throughs, not provider imports.** `endpoints/setup.py` used to call `providers.ocean.ofs.find_ofs_model()`, `providers.buoy.ndbc.discover_stations()`, `providers.tides.coops.discover_stations()`, and `providers.marine.grib_processor` directly to answer four setup-time questions (covering OFS model, nearby buoy/tide stations, GRIB2 backend availability). Per the marine-service-add-on invariant above, the API now calls the marine service instead — `services/companion_proxy.py`'s `marine_discovery_get()` issues a direct authenticated GET to `{marine_service_url}/discovery/{buoy-stations,tide-stations,ofs-model,grib-availability}` (pinned contract, separate from the manifest-driven `/api/v1/*` proxy routes above it, since these are one-off wizard lookups, not cacheable dashboard resources). The wizard's own endpoint paths and response shapes are unchanged. `marine_service_url` unconfigured and marine-service-unreachable are distinct, honest 503s (`MarineDiscoveryUnconfiguredError` / `MarineDiscoveryUnavailableError`) — the wizard never receives an empty station list standing in for "the marine service couldn't be reached."

Bathymetry data for SWAN grids is accessed through `bathymetry_resolver.py` in the marine service (`weewx_clearskies_marine/services/bathymetry_resolver.py`), which implements a priority chain: operator-supplied file → NCEI regional coastal DEM (OPeNDAP) → USGS Great Lakes DEM (GeoTIFF) → CRM/DEM_all fallback. The resolver uses a static JSON index of 199 NCEI regional DEMs (`data/ncei_regional_dem_index.json`, built offline by `scripts/build_ncei_dem_index.py`). Vertical datum consistency is enforced by matching the CO-OPS tide prediction datum to the bathymetry DEM's native datum (ADR-098). No local datum conversion for the common case. The marine service's `swan.py`'s `download_bathymetry_for_level(domain, level, allow_download=...)` consults the resolver before falling back to the legacy CRM `getSamples` endpoint — but only when `allow_download=True`, the apply-time chain's default. **At SWAN runtime (T4A.3) `allow_download=False`**: a missing cache is an ERROR and that SWAN run is aborted (C-77/C-90, 2026-07-26 — it does **not** fall back to a uniform 15 m depth; that fallback is deleted); a stale (>180 day) cache is used anyway with a WARNING rather than triggering a download — staleness only resolves on the next marine config push (`POST /config` on the marine service).

**Coordinate frame for SWAN grids (audit finding F1, operator ruling 2026-07-28, Option A):** SWAN runs in a Cartesian (UTM-projected) frame — a UTM zone is a 6°-wide strip with its own flat projection, and SWAN has no concept of zones. All lat/lon→UTM projections for a deployment's L1/L2/L3/L4 grid nest use ONE UTM zone, locked at grid-sizing time from the deployment's surf-spot centroid (`services/grid_sizing_chain.py`'s `run_grid_sizing_chain()`, persisted as `DomainSizing.locked_utm_zone` in the `swan_grid_sizing.json` cache and threaded to every projection call in `services/swan_formats.py`/`services/swan_runner.py`) — never a per-grid zone recomputed from each grid's own centroid, which could otherwise put a wide L1 approach grid and a tight per-cluster L3/L4 grid in different UTM zones near a 6° zone seam and silently zero the nested wave energy. A setup-time width guard on the same centroid computation logs a WARNING when the configured surf spots span more than 1° of longitude (unusually wide, still sized as one nest) and REFUSES the config (no sizing produced) above 2° — a misconfiguration guard, not an accuracy limit. Genuinely multi-region deployments (surf spots approaching the coast from separate shelves/regions, needing separate L1 nests) are not supported and must be split into separate regional deployments; the refuse threshold is what surfaces that case to the operator. **Antimeridian/Pacific deployments are supported** (audit finding F2, operator ruling 2026-07-28: the product is not scoped to US coasts): the centroid and the width-guard span are both computed wrap-aware (circular mean of longitude; span via the minimal enclosing arc, not `max−min`), so a deployment straddling ±180° measures as its true (narrow) extent rather than being misread as ~360° wide and spuriously refused. This is unrelated to the genuinely-multi-region carve-out above — a single deployment that happens to sit on the antimeridian is still one deployment, one locked zone.

Shared utility: `_common/nws_zones.py` — marine zone discovery (station → CWA → zone list → polygon proximity). Used by NWS marine text, NWS SRF, and the marine zone alerts extension.

Provider subdirectories `marine/`, `tides/`, `buoy/`, `wind/`, `ocean/`, and `nearshore/` — and the `[nearshore]` pip extra — have moved entirely to the `weewx-clearskies-marine` repo. The API `providers/` directory retains only `_common/`, `forecast/`, `aqi/`, `alerts/`, `earthquakes/`, `seeing/`, and `radar/`. All marine, tidal, buoy, wind, ocean, and nearshore provider logic runs exclusively in the marine service. The `[marine]` pip extra is also removed from the API.

> **eccodes native dependency (marine service):** GRIB2 processing (HRRR wind fields for SWAN, WaveWatch III boundary conditions) runs in the marine service, not the API. The marine service's `[nearshore]` pip extra includes eccodes; native installs on the marine service host require the system library first (`sudo apt install libeccodes-dev` on Debian/Ubuntu). The API has no eccodes dependency and no `[marine]` or `[nearshore]` pip extra. See OPERATIONS-MANUAL §1.
