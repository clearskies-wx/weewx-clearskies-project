## Q1 — Consumer contract: `providers/marine/wavewatch.py` + its three `endpoints/marine.py` call sites

9 fields, all wave-derived. **No windSpeed/windDirection** — the module docstring (`wavewatch.py:53-63`) records this was an explicit coordinator-approved drop because the PacIOOS `ww3_global` ERDDAP dataset carries no true 10 m wind. ### `wave_source = "wavewatch+ndbc+nws_marine"` (`:645`)

**Not a data blend/merge algorithm.** It is a static, hardcoded descriptive string literal assigned unconditionally and placed on `bundle.source` (`MarineBundle.source`, `:654`). It labels which three provider families *could* have contributed data to the bundle (wavewatch forecast + NDBC observation + NWS marine zone text) — it does not reflect whether any of the three actually succeeded for a given request (each is independently try/excepted upstream; a client reading `source` cannot tell if wavewatch silently failed). No merge/weighting/selection logic exists at `:645` or nearby — the actual per-field source precedence is scattered across the three call sites documented above (waveHeight: wavewatch → NDBC fallback; waterTemp: OFS resolver → NDBC fallback, `:464-478` and `:579-629`).

### eccodes `shortName` vs NCEP/NOMADS variable name — confirmed mismatch, live-parsed

Downloaded the two subsetted samples to the scratchpad dir and read them with the repo's own `.venv-round4` (has `eccodes` installed) using `grib_processor.py`'s own extraction pattern. **The NOMADS/`.idx` variable names (`HTSGW`, `WVHGT`, `WVPER`, `SWELL`, `SWPER`) are NOT the eccodes `shortName` values** `grib_processor.py`'s `read_grib_fields()` matches against:

| NOMADS/`.idx` name (what you request in the URL) | eccodes `shortName` (what `read_grib_fields()` must be told to look for) | eccodes `name` |
|---|---|---|
| `HTSGW` | `swh` | Significant height of combined wind waves and swell |
| `PERPW` | `perpw` | Primary wave mean period |
| `DIRPW` | `dirpw` | Primary wave direction |
| `WVHGT` | `shww` | Significant height of wind waves |
| `WVPER` | `mpww` | Mean period of wind waves |
| `WVDIR` | `wvdir` | Direction of wind waves |
| `SWELL` (partitions 1-3) | `shts` (all 3 partitions share this shortName; only `level` 1/2/3 distinguishes them) | Significant height of total swell |
| `SWPER` (partitions 1-3) | `mpts` | Mean period of total swell |
| `SWDIR` (partitions 1-3) | `swdir` | Direction of swell waves |

Every message additionally carries `missingValue = 9999` (confirmed live, both samples) and `Ni`/`Nj` sized correctly for the requested bbox at 0.16°.

**Critical gap for SW-2 design, not something I fixed (read-only task):** `grib_processor.py`'s `_read_eccodes()`/`_read_pygrib()` key `result.fields` **by `short_name` alone** (`grib_processor.py:159`, `:217` — `result.fields[short_name] = GribFieldData(...)`). For the 3 swell partitions, all 3 GRIB messages share the SAME `shortName` (`shts`/`mpts`/`swdir`) and differ only by `level` (1/2/3) — as currently written, `read_grib_fields()` would silently keep only the **last-read** partition message per shortName and overwrite the other two in the dict, because there is no level-aware key. This machinery was built for HRRR/GFS wind (2 distinct shortNames, `10u`/`10v`, no partition collision) and was never exercised against a multi-partition field. SW-2 will need either a level-aware extension to `GribResult`/`read_grib_fields()` or a parallel partition-aware reader — flagging as a fact, not proposing the fix (architectural surface, not mine to decide).

## Q3 — In-repo GRIB machinery: what's reusable

### `grib_processor.py` (`weewx_clearskies_marine/providers/marine/grib_processor.py`)

- **Backend selection** (`:35-49`): try `eccodes` import, fall back to `pygrib`, else `GRIB_AVAILABLE = False` and importing the module does not crash (`check_grib_available()` raises with platform install instructions only when a caller actually needs GRIB, `:62-67`).
- **`read_grib_fields(file_path, field_names, target_step=None)`** (`:243-287`): opens one GRIB2 file, iterates every message, keeps ones whose `shortName` is in the requested set (optionally also matching `endStep == target_step`), returns a `GribResult` (dict of `shortName → GribFieldData`, 2-D `values` as **pure Python lists**, no numpy — comment at `:4` says this is deliberate, "HRRR and SWAN grids are tractable in pure Python"). **As documented above, this is shortName-keyed only — no level/partition axis.**
- **`extract_nearest_value()`** / **`bilinear_interpolate()`** (`:290-378`): point extraction from a `GribFieldData` grid, missing-sentinel check is `val >= 9.999e20` (a different, hardcoded sentinel from the `9999` this repo's own ww3_spectrum.py docstring says is the real GRIB `missingValue` for these products — **potential mismatch to check**: the live-verified `missingValue` on the gfswave sample was `9999`, not `9.999e20`; `9.999e20` is the classic GRIB1/generic missing-data convention used by HRRR fields, not necessarily what gfswave uses. This function does not read `missingValue` from the message itself; it hardcodes `9.999e20`. If gfswave truly uses `9999` as its sentinel, values near the coast/land-masked cells would NOT be filtered by this function as currently written — a real correctness risk for SW-2, not something I'm authorized to fix here.)
- **`apply_breaking_limit()`/`compute_breaker_gamma()`** (`:386-449`): unrelated wave-breaking physics, not GRIB I/O — irrelevant to SW-2.

### `providers/wind/hrrr.py` and `providers/wind/gfs.py` — the established fetch pattern

Both are structurally near-identical and both are directly reusable as a template:

1. **Sync, not async.** `ProviderHTTPClient` is `httpx.Client` (sync), rate-paced with `time.sleep(0.55)` between per-forecast-hour requests inside the loop (`hrrr.py:828`, `gfs.py:639`) — not asyncio.
2. **NOMADS Grib Filter, subsetted, one HTTP GET per forecast hour** (not full-file, not S3). URL built manually (not `httpx params=`) because NOMADS is sensitive to param ordering/empty-string values (`hrrr.py:575-577`, `gfs.py:432-434`) — same reasoning applies to `filter_gfswave.pl`.
3. **Rate limiting via a dedicated `RateLimiter` instance** per provider (`hrrr-wind`, `gfs-wind` — 2 req/s), NOT built into `ProviderHTTPClient` itself — `ProviderHTTPClient` only owns timeout/retry/TLS/UA (`http.py:1-22`; confirmed `max_retries=2`, exponential backoff 0.5s×2^n capped at 5s, ±25% jitter, 4xx never retried).
4. **GRIB2 magic-byte sniff before parsing**: `content[:4] != b"GRIB"` → treat as absent/HTML-error-page, return `None` rather than attempt a parse (`hrrr.py:697-704`, `gfs.py:542-549`). Directly reusable for gfswave.
5. **Tmp file lifecycle**: `tempfile.mkstemp(suffix=".grib2", prefix="hrrr_"/"gfs_")`, written via raw `os.write`/`os.close`, then `os.unlink()` in a `finally` immediately after `grib_processor` extraction — one file per forecast hour, never batched, never left behind on any exit path (`hrrr.py:706-712` + `:859-863`; `gfs.py:551-557` + `:673-677`).
6. **eccodes/pygrib dual backend detected independently in each provider module** (not shared from `grib_processor.py`'s own detection — `hrrr.py`/`gfs.py` both re-import and re-detect `eccodes`/`pygrib` themselves at `:73-87`, duplicate of `grib_processor.py`'s own `:35-49` logic). `hrrr.py`/`gfs.py` do NOT call `grib_processor.read_grib_fields()` at all — they have their **own** private `_extract_eccodes`/`_extract_pygrib` functions (`hrrr.py:295-427/434-535`, `gfs.py:198-308/315-392`) that read UGRD/VGRD directly, because HRRR additionally needs Lambert-Conformal projection metadata (`LovInDegrees`/`Latin1InDegrees`/`Latin2InDegrees`) that `grib_processor.py`'s generic `GribFieldData` doesn't carry. **`grib_processor.py` is used elsewhere (SWAN nearshore output, per its own docstring `:15`) but NOT by the two existing wind providers** — SW-2 has a real choice between reusing `grib_processor.read_grib_fields()` (generic, shortName-keyed, needs the level-aware fix noted in Q2) or writing a dedicated extractor like HRRR/GFS did (more code, but sidesteps the partition-collision gap cleanly since a bespoke extractor can key on `(shortName, level)` from the start).
7. **CAPABILITY conditional on `GRIB_AVAILABLE`** (`hrrr.py:111-144`, `gfs.py:114-149`): `CAPABILITY = None` when no backend is present, so dispatch registration simply skips the provider rather than crashing.

### eccodes availability confirmed locally

`.venv-round4/Scripts/python.exe` (this repo's own venv) has `eccodes` installed and working — used directly to parse both scratchpad GRIB samples (see Q2). No install was performed; the venv already had it.

## Q4 — Cycle handling (file:line-cited)

### HRRR (`hrrr.py`)

- `_compute_hrrr_cycle(now, extended_only)` (`:641-666`): current UTC hour minus `_CYCLE_AVAILABILITY_LAG = 1h`, floored to the hour; if `extended_only` (needed for 48h+ requests), snapped down further to the nearest of `{0,6,12,18}` (HRRR's extended-forecast cycles).
- Fallback loop in `fetch()` (`:806-847`): tries up to `_MAX_CYCLE_FALLBACKS = 2` earlier cycles (3 attempts total), stepping back 1h (or 6h if `extended_only`) each attempt. **f00 404 → try earlier cycle; a later hour 404 (f00 succeeded) → stop, cycle exhausted, keep what was fetched** (distinct handling — not just "any 404 → next cycle").
- All-cycles-exhausted → raises `ProviderUnavailableError` (`:932-939`), not silence.

### GFS (`gfs.py`)

- `_compute_gfs_cycle(now)` (`:495-511`): current UTC minus `_CYCLE_AVAILABILITY_LAG = 4h30m`, snapped down to `{0,6,12,18}`.
- Fallback loop (`:619-661`): `_MAX_CYCLE_FALLBACKS = 2` (3 attempts), stepping back a full 6h cycle each attempt. Same first-hour-vs-later-hour 404 distinction as HRRR.
- Exhausted → `ProviderUnavailableError` (`:722-729`).

### WaveWatch III / ERDDAP (`wavewatch.py`, for comparison — this is the pattern PROVIDER-MANUAL §14.3 calls the "3 previous cycles" idiom)

- `_compute_model_cycle(now)` (`:286-295`): now minus `_CYCLE_AVAILABILITY_LAG_HOURS = 4.5h`, floored to `{0,6,12,18}`.
- Fallback loop (`:520-548`): `_MAX_CYCLE_FALLBACKS = 3` (4 attempts total — one more than HRRR/GFS), stepping back `_CYCLE_STEP_HOURS = 6` each attempt. On 404 → try earlier; on 200-but-empty-forecast → also try earlier (ERDDAP has no partial-cycle concept the way NOMADS forecast-hour-by-hour does).
- Exhausted → does NOT raise; returns empty `forecast` list with the last-attempted cycle's ISO time as `model_run` (`:550-561`) — **different failure mode from HRRR/GFS** (silent-empty vs raise).

**For SW-2 (gfswave GRIB, mirroring the wind providers' same-product retry per the task's framing):** GFS wave model runs on the same cadence as GFS itself (00/06/12/18Z, same NOMADS host, same `gfs.YYYYMMDD/CC/` directory root) — `gfs.py`'s `_compute_gfs_cycle`/fallback-loop shape (6h lag, `{0,6,12,18}` snap, step-back-6h fallback, `ProviderUnavailableError` on exhaustion) is the closer structural analog than HRRR's, not wavewatch's own ERDDAP-specific 4.5h-lag/silent-empty pattern — flagging this as an observation for the lead to weigh, not a decision I'm making.

## Q5 — Refusal shape: provider-error taxonomy and what the endpoint does with it

### Taxonomy (`providers/_common/errors.py`, full file read)

```
ProviderError (base)               — .provider_id, .domain, .retry_after_seconds, .status_code
├── QuotaExhausted                 → 503 + Retry-After
├── KeyInvalid                     → 502
├── GeographicallyUnsupported      → 503
├── FieldUnsupported                → 502
├── TransientNetworkError          → 502
├── ProviderUnavailableError       → 503  (data not yet published, all cycle fallbacks exhausted)
└── ProviderProtocolError          → 502  (response shape unexpected; logged ERROR)
```

Dispatch is by exception **attribute** (`status_code`, `retry_after_seconds`), never by parsing the message string (rules/coding.md §3, enforced in the docstring itself, `errors.py:10-13`).

### App-level HTTP mapping — DOES exist and IS wired (`weewx_clearskies_marine/errors.py:74-118`)

`register_error_handlers(app)` installs a global FastAPI `@app.exception_handler(ProviderError)` that maps `QuotaExhausted`/`GeographicallyUnsupported` → 503 (+`Retry-After` header if set), everything else in the taxonomy → 502, and emits an RFC 9457 `application/problem+json` body (`type`, `title`, `status`, `detail`, `providerId`, `domain`, `errorCode`, optional `retryAfterSeconds`) — full 502-class logged at ERROR, 503-class at WARNING (`errors.py:85-99`). This is real, live-wired machinery, not aspirational.

### But `endpoints/marine.py`'s wavewatch call sites never let it fire

**This is the load-bearing finding for SW-2.** All three wavewatch call sites (`:216-228`, `:430-442`, `:569-577`) wrap `wavewatch.fetch()` in a bare `try: ... except Exception:` that **logs a WARNING and silently continues** — `current_conditions`/`observation` simply keep whatever the NDBC fallback already produced, `forecast` stays `[]`. **A `ProviderError` raised inside `wavewatch.fetch()` is caught by this generic `except Exception:` before it can ever reach `register_error_handlers()`'s `ProviderError` handler.** The RFC 9457 502/503 machinery in `weewx_clearskies_marine/errors.py` is real and correctly wired for whatever call path DOES let a `ProviderError` propagate uncaught (I did not audit every endpoint in the repo for this — out of scope), but **wavewatch inside `endpoints/marine.py` today is not one of them.** The net client-visible behavior of a total wavewatch outage today is **degrade-to-partial** (missing waveHeight/forecast, HTTP 200 still returned with `null`/`[]` in the relevant fields) — never a 502/503.

**This is exactly the semantic the operator's ruling changes.** "Refuse on failure" (register item 10) is a different contract than what's live today for wavewatch's three call sites — landing SW-2's ERDDAP deletion "on the existing refusal semantics" (as the task brief puts it) means the existing semantics for wavewatch specifically are **best-effort/degrade**, and matching the operator's ruling will require the new gfswave GRIB provider's failure path to NOT be caught by a bare `except Exception:` the way ERDDAP's is today — i.e. the call sites' own try/except shape, not just the provider module, needs to change for refusal to actually surface. Flagging this as a fact for the SW-2 brief; not proposing which of the three call sites to change or how (architectural surface — the task scope for this fact-pin is read-only).

**`wavewatch.py` is ocean-only today. No Great Lakes handling exists in the module.** Confirmed by: (a) a repo-wide grep for `Great Lakes|GLWU|glwu` across `weewx_clearskies_marine/` returns 15 files, and `providers/marine/wavewatch.py` is **not** among them; (b) `_GRIDS` (`wavewatch.py:207-216`) has exactly one entry, the PacIOOS `ww3_global` ocean dataset — a global ocean WW3 run masks/excludes enclosed lakes (no explicit lat/lon carve-out needed in `_select_grid()` because the dataset itself has no Great Lakes data to serve, though this specific masking behavior was not independently re-verified against a live Great Lakes point query — noted as a gap, not a downloaded/tested fact).

**Great Lakes WW3 GRIB IS already used elsewhere in this repo** — `services/ww3_spectrum.py` and `services/ww3_station_selection.py` fetch the **station spectral** (`.spec`) GLWU product for the SWAN L1 boundary (PROVIDER-MANUAL §14.3a/§14.3b), and route product selection (`product_for_extent()`, described in §14.3b) between ocean `gfswave` and Great Lakes `glwu` by classifying the SWAN domain's centre via `enrichment/bathymetry.py`'s `classify_region()`.

**The equivalent GLWU *gridded* GRIB2 product exists and was live-verified today** (not previously documented anywhere in this repo that I found): `glwu.grlc_2p5km.tCCz.grib2` — verified live at `https://nomads.ncep.noaa.gov/pub/data/nccf/com/glwu/prod/glwu.20260806/` (also `glwu.grlc_2p5km_lc.tCCz.grib2` and `glwu.grlc_2p5km_lc_sr.tCCz.grib2` variants present — not investigated further, naming suggests "land/coast masked" and "super-resolution" variants; base `glwu.grlc_2p5km` is the plain product). Its `.idx` (`.../glwu.20260806/glwu.grlc_2p5km.t01z.grib2.idx`) shows the **identical 19-entry-per-cycle field layout** as `gfswave` (WIND/WDIR/UGRD/VGRD/HTSGW/PERPW/DIRPW/WVHGT/SWELL×3/WVPER/SWPER×3/WVDIR/SWDIR×3) — same field names, same 3 swell partitions.

**One structural difference worth flagging:** GLWU's gridded GRIB2 file bundles **every forecast hour into one file** (the `.idx` shows repeating `WIND:surface:anl`, then `WIND:surface:1 hour fcst`, `2 hour fcst`, etc., all in the same `glwu.grlc_2p5km.tCCz.grib2`) — unlike `gfswave`'s one-file-per-forecast-hour layout. A GLWU fetch would need `target_step`-based filtering within a single larger download rather than HRRR/GFS's per-hour-file loop pattern. Cycle cadence: hourly (`bulls.t00z` through `t04z`+ observed in the `glwu.20260806/` listing, consistent with PROVIDER-MANUAL §14.3b's "GLWU publishes hourly" statement).

**Whether GL is in scope for SW-2's display-provider replacement is a lead/operator decision** — this fact-pin only confirms the product exists and its shape; wavewatch.py itself has never served Great Lakes locations.
