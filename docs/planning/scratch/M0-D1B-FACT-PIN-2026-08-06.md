## Q1 — WRITER: where per-transect 2-D spectra get attached into `spectral`

**Two independent producers write into `SWANRunner._spectral_results[spot_id]`**,
which `providers/nearshore/swan.py` reads directly into `payload["spectral"]`
at `swan.py:3480` (`"spectral": spectral_results.get(spot_id, [])`, where
`spectral_results = getattr(runner, "_spectral_results", {})` at `swan.py:3301`).

### Producer A — L3/L4-enabled spots (T4B.3), `services/swan_runner.py:6044-6242`

This is the path that runs for the deployed 162-transect HB-pier spot.

1. `_select_l3_handoff_position_and_spectrum()` (`swan_runner.py:715-1105`) is
   called once per transect per timestep (`swan_runner.py:6152-6172`). It
   selects the handoff **position** from the transect's own 10 m band, reads
   the **spectrum** (`freqs_hz`/`dirs_deg`/`energy`) from the nearest shared
   CURVE SPECOUT station, and reads **components** from the transect's own
   `TABLE_PT_*` PT* columns (T4B.6, `pt_table_text=_t_table_text`,
   `swan_runner.py:6159-6172`). Each call returns one dict per timestep,
   appended at `swan_runner.py:1046-1055`:
   ```
   {"time", "components", "freqs_hz", "dirs_deg", "energy",
    "handoff_depth_m", "handoff_source_level", "clamped"}
   ```
2. Per-transect per-timestep results are folded into
   `_by_transect_by_time[transect_index][time] = entry` (`swan_runner.py:6175-6178`).
3. A "carrier" list is built — one dict per timestep, keyed
   `{"time": ..., "handoff_by_transect": {transect_index: entry_minus_time}}`
   (`swan_runner.py:6200-6215`, `time` key explicitly stripped from each
   per-transect entry at `6209-6211`), and this carrier list **replaces**
   `self._spectral_results[spot_id]` (`swan_runner.py:6217`).

**Exact schema of one `spectral` list entry (L3/L4-enabled spot), at HEAD:**
```
{
  "time": "<ISO-8601 UTC>",
  "handoff_by_transect": {
    <transect_index:int>: {
      "components": [...],          # SpectralWaveComponent-shaped dicts
      "freqs_hz": [...],            # 1-D array
      "dirs_deg": [...],            # 1-D array
      "energy": [[...], ...],       # 2-D array, E[i_freq][i_dir]
      "handoff_depth_m": float,
      "handoff_source_level": "L3" | "L4",
      "clamped": bool
    },
    ... one entry per transect that resolved a handoff this hour ...
  }
}
```
No top-level `freqs_hz`/`dirs_deg`/`energy`/`components` on this entry shape —
the carrier list built at `swan_runner.py:6203-6215` only ever sets `time` and
`handoff_by_transect`. Explicit code comment confirming the 2-D field is
carried but structurally unused by the consumer (`swan_runner.py:6235-6239`):
> "The 2-D spectrum (freqs/dirs/energy) carried on each entry still comes
> from the nearest CURVE SPECOUT station, but the surf 1-D pipeline consumes
> only the per-transect components, not that 2-D field."

### Producer B — L3-disabled spots, L2 DWR fallback (T4B.4), `swan_runner.py:3532-3726`

1. Spot-level DWR baseline entries are built first (`swan_runner.py:3587-3593`):
   `{"time", "freqs_hz", "dirs_deg", "energy", "components"}`, assigned to
   both `self._spectral_results[_sid]` and `self._spectral_dwr_results[_sid]`
   (`swan_runner.py:3614-3615`) — the two start as the SAME list object for
   an L3-disabled spot (ADR-095 Amendment 1 §2).
2. `T4B.4` then parses one extra per-transect-cell DWR SPECOUT per distinct L2
   cell the spot's transects fall into (`swan_runner.py:3641-3702`), each
   entry shaped:
   ```
   {"freqs_hz", "dirs_deg", "energy", "components",
    "handoff_depth_m": L2_REFERENCE_DEPTH_M, "handoff_source_level": "L2"}
   ```
   (`swan_runner.py:3695-3702` — no `"clamped"` key on this path, confirmed
   also by `surf_pipeline_timestep.py:254`).
3. These are attached ADDITIVELY as `_base["handoff_by_transect"] = _tb`
   (`swan_runner.py:3718`) onto the SAME entries `spectral`/`spectral_dwr`
   both point to — so for an L3-disabled spot, `spectral[i]` still carries
   its own top-level `freqs_hz`/`dirs_deg`/`energy`/`components` **plus** a
   `handoff_by_transect` dict (transects sharing an L2 cell share one
   sub-entry).

## Q3 — SAME-CYCLE consumers after `cache.set()`

**No same-cycle consumer reads the heavy arrays back out of the in-memory
cache after `cache.set()` runs**, in either the full-run or quick-update path.

- Full run (`_run_all_spots_locked()`): the only same-cycle consumer of
  `spectral_results[spot_id]`'s heavy arrays is `_precompute_swelltrack_for_spot()`,
  and it receives them as a **direct function argument** from the runner's
  own in-memory attribute (`spectral_results.get(spot_id, [])`, `swan.py:3511`)
  — called at `swan.py:3508-3518`, **before** `cache.set()` at `swan.py:3531-3535`.
  It never calls `fetch()`/`cache.get()` for this spot's own data.
- After `cache.set()`, the per-spot loop (`swan.py:3402-3537`) moves to the
  next spot; nothing re-reads the just-written entry.
- The only in-process `fetch()`/`cache.get()` calls anywhere in `swan.py` are:
  `swan.py:3199` and `swan.py:3946` (T7.2 wave-setup, read the **prior**
  cycle's `transect` key, not `spectral`), and `swan.py:4045`
  (`_run_quick_update_locked()`'s own read-modify-write of `last_good`,
  which never touches `last_good["spectral"]` — see Q1/Q6).

**Consequence:** trimming the `energy`/`freqs_hz`/`dirs_deg` arrays out of
`payload["spectral"]` would be safe for same-cycle consumers **whether done
before `cache.set()` (trims the in-memory `TTLCache` entry too) or only at
persist time** (`_persist_forecast_cache_to_disk()`/`_update_forecast_cache_on_disk()`,
leaving the in-memory copy untrimmed). The two are NOT equivalent for the
OOM symptom, though: since (per Q2) nothing ever reads the arrays back out
of the in-memory cache either, trimming ONLY at persist time would leave the
full untrimmed arrays sitting in the in-process `TTLCache` for up to
`_LAST_GOOD_TTL_SECONDS` (7 days, `swan.py:197`) for every spot from every
full run — i.e. a persist-time-only trim would shrink the on-disk file and
the next restart's parse, but would **not** address the live-process RSS
candidate (#2 in the OOM investigation) that accumulates across cycles in
the running process. This is a factual consequence of the code as read, not
a fix recommendation.

## Q4 — POST-RESTART: what touches the 2-D arrays from a restored cache

Restore path: `_load_forecast_cache_from_disk()` (`swan.py:1482-1546`) does
`cache.set(_build_last_good_key(spot_id), payload, _LAST_GOOD_TTL_SECONDS)`
for every spot verbatim from the on-disk JSON (`swan.py:1537-1539`) — no
transformation, so whatever shape was persisted is exactly what `fetch()`
serves afterward.

Given Q2's finding that **no live reader touches the 2-D arrays at all**
(not `endpoints/surf.py`, not `endpoints/beach_profile.py`, not
`surf_pipeline_timestep.py`, not `surf_1d_pipeline.run_pipeline()`), the
answer is uniform across every code path that could run against a restored,
pre-full-run cache:

- **If persisted `spectral` entries carried `components`/`handoff_depth_m`/
  `handoff_source_level`/`clamped` only, with `freqs_hz`/`dirs_deg`/`energy`
  absent:** every consumer identified in Q2 continues to work exactly as
  today — `.get("components")` (`surf_1d_pipeline.py:2218`) and
  `.get("handoff_depth_m")`/`.get("handoff_source_level")`/`.get("clamped")`
  (`surf_pipeline_timestep.py:289-293`) are unaffected by the missing keys;
  no code path calls `.get("freqs_hz")`/`.get("dirs_deg")`/`.get("energy")`
  on a cached `spectral` entry anywhere in the enumerated readers.
- Classification: **"serves without arrays" and functionally identical to
  today** — not "recomputes on demand" (nothing recomputes a spectrum from
  the 2-D fields — T4B.2's no-silent-fallback rule, `surf_1d_pipeline.py:2122-2137`,
  explicitly forbids that), not "fails loudly" (no code path raises/logs on
  their absence — they're never `.get()`-checked), not "fails silently" in
  the sense of a masked defect (there is no defect being masked; the fields
  are provably unread).
- The only degradation risk is **outside this repo's control flow**: an
  external consumer (a debug script, a manual `/health`-style raw dump, a
  future feature) that reads the raw cache file directly and expects the
  2-D arrays would silently get empty/absent data. No such consumer was
  found in this repo (see Q2's grep sweep) — flagged as a "could not fully
  rule out an out-of-repo consumer" caveat in the section below.

## Q5 — PRECEDENT: `swelltrack_cache.py`'s trimmed codec, `chunked_json.py`

### `services/swelltrack_cache.py` (whole file read)

Encodes a `PipelineResult` for the precomputed swelltrack cache
(`serialize_pipeline_result_for_cache()`, `:123-170`). Deliberately **drops
three fields from every `TransectResult`**: `hs_total_profile`, `distances`,
`depths` (`_transect_result_to_dict()`, `:84-95`; module docstring `:10-12`).
Measured tradeoff documented in the module docstring (`:14-24`): full
encode (30 transects, ~594 pts each) = 558 KB/timestep/spot, ~39 MB/spot/cycle,
~196 MB/5 spots/cycle; trimmed = 5.2 KB/timestep, ~0.37 MB/spot/cycle,
~1.84 MB/5 spots — a >100× reduction from dropping exactly the fields no
live reader needs.

**Read-side tolerance of absence:** `_transect_result_from_dict()`
(`:205-227`) reconstructs `TransectResult` with `hs_total_profile=empty`,
`distances=empty`, `depths=empty` (`np.array([], dtype=float)`,
`:214-220`) — never raises for their absence, because they were never
written in the first place. Docstring (`:206-212`) states explicitly: "Any
caller that reads them off a cache-hit result gets empty arrays back, not
an error — `surf.py` does not read them ... this is safe for its use.
Do not route `beach_profile.py` through this decoder; it needs the real
arrays" (i.e. `beach_profile.py` deliberately bypasses this trimmed cache
and always runs on-demand for the one array-consuming case that exists).
The rest of `deserialize_pipeline_result_from_cache()` (`:255-331`) uses
`.get(key, default)` throughout for every field added after the cache
format's original version (BD-7/BD-9, C4/G7.5, D10.2), so old cache
entries missing newer keys deserialize cleanly rather than raising.

**This is the in-repo precedent model**: drop fields no reader needs at
encode time; have the decoder default the dropped fields to an inert empty
value rather than erroring, with an explicit comment steering future
readers away from adding a real consumer of the dropped shape without
first re-measuring.

### `services/chunked_json.py:dumps_chunked()` (whole file read)

Encode-side-only chunked JSON encoder (H4, MARINE-FORWARD-PLAN.md task H4).
Recurses into dict values (by key, insertion order) and "large enough" list
values (by element, batched in slices of `list_slice_size`, default 100),
yielding the GIL via a **real, non-zero sleep** (`time.sleep(list_yield_sleep_s)`
/`time.sleep(dict_yield_sleep_s)`, both default `0.0005`s) every
`list_yield_stride`/`dict_yield_stride` slices/keys (both default 50) —
`time.sleep(0)` was measured and rejected as an unreliable GIL hand-off
(module docstring `:119-144`). Byte-identical output to plain `json.dumps()`
for the same arguments (KAT'd, module docstring `:46-56`). Default
`max_depth=4` matches the SWAN forecast cache's own shape exactly (module
docstring `:58-68`: depth 0 = top-level `{"saved_at","spots"}`, depth 1 =
per-spot payload, depth 2 = each spot's own keys incl. `spectral`, depth 3+
recurses into dict-shaped sub-keys like `transect`/`swelltrack`). Both
`_persist_forecast_cache_to_disk()` and `_update_forecast_cache_on_disk()`
call `dumps_chunked(data)` with all defaults (`swan.py:1382`, `swan.py:1464`).

**Decode is explicitly out of scope** — `dumps_chunked()` has no decode
counterpart; `json.loads()` stays monolithic everywhere it's called.

### H4 lead-ruling comment, `swan.py:1454-1463` (verbatim, quoted exactly)

> "H4: encode side only -- see `_persist_forecast_cache_to_disk()`'s comment
> for the mechanism/measurement. The read/decode above (`json.loads(raw)`,
> `:1423`) stays monolithic this round (lead ruling 2026-08-02): no
> streaming JSON parser exists in the stdlib without a new dependency (not
> approved), and this is the hourly quick-update/"fill" path's OWN read of
> the existing disk cache, not a decode of what THIS call is about to
> write. A residual ~1.3 s GIL hold remains there -- see this round's
> closeout."

Confirmed also restated in `chunked_json.py:146-155`: "Decode (`json.loads()`)
is explicitly OUT of scope this round (lead ruling 2026-08-02) -- no
streaming/incremental JSON parser exists in the stdlib without a
third-party dependency (not approved, architectural trigger 7), and this
module does not attempt one." **D-1b's implementation must not introduce a
new decode dependency — that ruling stands, unchanged by this fact-pin.**

## Q6 — TTLs, and the accumulation mechanism

- `_FORECAST_CACHE_MAX_AGE_S = 12 * 3600` — 12 hours — `swan.py:238`, used
  at `swan.py:1525` in `_load_forecast_cache_from_disk()` to discard a
  stale on-disk cache at startup.
- `_LAST_GOOD_TTL_SECONDS = 604800` — 7 days — `swan.py:197`
  ("stale is always preferred to no data"), the in-memory `TTLCache` entry
  lifetime set by every `cache.set()` call for a spot's payload
  (`swan.py:1539`, `swan.py:3534`, `swan.py:4214`).
- **No pruning of old timesteps exists in the persisted file today.**
  Mechanism, confirmed by reading both write paths:
  - **Full run** (`_run_all_spots_locked()`): `payload["spectral"] =
    spectral_results.get(spot_id, [])` (`swan.py:3480`) builds a **brand
    new dict** every run from this cycle's own SWAN output only —
    `cache.set()` (`swan.py:3531-3535`) **replaces** the previous TTLCache
    entry wholesale, and `_persist_forecast_cache_to_disk(disk_payloads)`
    (`swan.py:3548`) writes the **entire file** fresh from
    `{"saved_at": ..., "spots": spots_data}` (`swan.py:1364-1367`) — this
    is a REPLACE of the whole on-disk file every full run, not an append.
  - **Quick update** (`_run_quick_update_locked()`): confirmed by reading
    the full merge loop (`swan.py:4028-4216`) — it **never writes
    `last_good["spectral"]`** at all. Only `forecast` (bounded
    closest-index replace-in-place, `swan.py:4053-4114`), `swelltrack`
    (bounded closest-key replace, `:4137-4172`), and `wind_for_display`
    (same pattern, `:4191-4211`) are merged, each capped at "replace the
    entry closest to this snapshot's time," never grown by appending a new
    key alongside an old one. `_update_forecast_cache_on_disk()`
    (`swan.py:1402-1480`) then merges `existing_spots.update(updated_spots)`
    (`swan.py:1435`) — a per-**spot** dict replace, not a per-key merge
    within a spot's payload, so a spot untouched by a given quick update
    keeps its exact prior payload (including its `spectral` list)
    byte-for-byte.
  - **Net: `spectral`'s size is set once per full run, by the size of that
    run's own SWAN output, and is never appended to.** There is no
    "old timesteps never pruned" bug in the sense of unbounded growth
    within a running process.
- **What actually explains 24 MB → 223 MB over 10 days, then:** feature
  landings, not runtime accumulation. `git log -S"handoff_by_transect"` on
  `swan_runner.py` shows the per-transect handoff carrier form (Producer A,
  Q1) was introduced by `f337648` "fix(surf): per-transect swell-spectrum
  handoff — retire the shared out-of-grid CURVE" (2026-07-30 12:33:54 -0700)
  and `d803d9c` "fix(swan): per-transect handoff no longer gated on
  single-line pick" (2026-07-29 21:38:05 -0700) — both squarely inside the
  reported 10-day growth window. Before these commits, a spot's `spectral`
  entries carried one 2-D spectrum per timestep (spot-level); after, an
  L3-enabled spot's entries carry one 2-D spectrum **per transect** (162×)
  **per timestep**, which is exactly the lead's measured 95.5%-of-file
  `spectral` breakdown. This reads as the size growth being a direct,
  expected consequence of a recent, intentional feature (more accurate
  per-transect handoff selection), not a latent pruning defect.
